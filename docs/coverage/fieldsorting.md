# FieldSortingCheck auto-fix coverage

The fixer parses field declarations in a class body and sorts them by the check's rules.
Enum constants are never reordered: their order is reported as a warning and never auto-fixed, and the fixer only splits constants sharing a line onto lines of their own, in the order written (see main table).

| Violation type | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| Chunk order | Non-final before final-with-value | Yes | Adds blank lines between chunks |
| Type order (prim vs ref) | `String name` before `int count` | Yes | Primitives sort before reference types |
| Type order (alphabetical) | `short` before `float` (same chunk) | Yes | Alphabetical by base type name |
| Array depth | `int[]` before `int` | Yes | Base type first, then arrays |
| C-style array declarator | `int elements[];` before `int codes;` | Yes | The declaration moves as whole lines. It is never merged into a same-type sibling nor rebuilt from its names, either of which would drop the per-declarator `[]` and silently retype that declarator |
| Annotation order | `@Nullable String` before `@NonNull String` | Yes | Unannotated first, then by canonical annotation key |
| Type-arg annotation order | `List<@B String>` before `List<@A String>` | Yes | Position-aware: compares type arguments left to right, unannotated before annotated, then alphabetical |
| Annotation consolidation | Same-type same-annotation fields on separate lines | Yes | Merges into single declaration after sorting, unless they are constants (a value written `static final`, or any interface or annotation-type field), which are sorted but left on their own lines |
| Name order | `int z` before `int a` (same type) | Yes | Case-insensitive alphabetical |
| Name order (within declaration) | `String zebra, alpha;` (one multi-name decl) | Yes | Reorders names in place (case-insensitive). Single-line, wrapped, and trailing-comment forms. A declaration that starts on a line opening with an annotation (`@Deprecated private int y, x;`) or sits below a multi-line annotation is rebuilt in place. Initialized names move with their initializers, in the order the initialized rows below give. See the skip rows below for the interior-comment and spanning-declarator forms |
| Interleaved opposite-static field | `int zebra;` `static int x;` `int alpha;` | Yes | Same-group fields are swapped into their existing physical slots; the interleaved opposite-static field stays put |
| Interleaved group spanning chunks or with dependencies | an interleaved reorder whose group is not a single dependency-free chunk | No | The in-place slot swap can't safely rebuild it; the fixer returns a `SkipResult` (`cannot reorder fields: an interleaved static or instance field is in the way`) |
| Interleaved field ordered past a multi-variable secondary name | `long alpha, zeta, beta;` `static int s;` `long gamma;` | No | The slot swap moves whole declarations and never reorders the names inside one, so `beta` cannot move ahead of `zeta`; the fixer returns the same interleaved `SkipResult` |
| Same-group fields separated by another member | `int beta = 1;`, a method, then `int alpha = 2;` | No | The rebuild emits only the fields' own lines, so the member between them would be deleted; the fixer returns a `SkipResult` (`cannot reorder fields: code between them belongs to no field`) |
| Same-line enum constant with annotation | `@Deprecated BETA, ALPHA` | Yes | Each constant's annotations are relocated above it one per line. A constant or comment sharing the annotation's first or last line is attributed to exactly one owner, so neither is duplicated or dropped |
| Same-line enum constant with text-block argument | `ALPHA("""x"""), BETA` | Yes | Each constant is emitted on its own line |
| Field dependencies | `B = A + 1` before `A = 0` | Yes | Respects dependency: A before B if B uses A, whether or not other fields sit between them. A bare `A` read ahead of its declaration does not compile, so moving `A` up fixes it, unless the two are pinned (see the row on a pinned pair read by bare name). A read counts when it names a field of the class: bare, or through `this`, or through `Outer.this` or the class's own name where `Outer` spells that class itself, simply, through its enclosing types or through its package (`Holder.this.count`, `Graph.Node.count`, `pkg.Graph.Node.count`). A member of another object or type (`other.count`, `super.count`, `System.out` beside an own `out`, `Adapter.this.count` in a `Holder` nested in `Adapter`, `Tree.Node.count` in another `Node`), a method's name (`this.size()`, `List.of(1).size()`, `T.this.b()`), a type's (a cast, a class literal, a `new`, a type argument), an annotation's, a label's (`break` or `continue`), a declaration's (a local class, enum, interface or record, its constructor, method, component or constant), a whole `case` label naming no constant variable of the class (`case RED ->` names the selector's enum constant), and a name the initializer binds itself (a lambda parameter, a method or constructor parameter of a local class, a local of a lambda or switch-arm block declared ahead of it, a for, catch or resource variable inside its own statement) are no read. A local class's or record's own field or component named like a field is still taken for it, which may only over-constrain the order |
| Two fields whose initializers may not trade places (pinned) | `int zeta = Ids.next();` before `int alpha = Ids.next();`, `static final Object TIMEOUT = readTimeout();` below `LOG`, `final Recorder recorder = new Recorder();` (an inner class reading `log`) below `log`, an anonymous class whose constructor or initializer runs a method reading a later field, `int clockWidth = ((Widget) register("clock", new Widget(120))).width;` below `WIDGETS = new HashMap<>()`, a nested type's `int RATE = sampleRate;` (which initializes the enclosing class) beside `NAMES = new ArrayList<>()`, `final String tag = "session:" + this;` below `user` | Yes (order kept) | What an initializer reads or runs, and what that code reads or writes, cannot be told from the source, so only an initializer built from literals alone is trusted not to observe the order of the fields: literals and text blocks; unary, binary, conditional, comparison and bitwise operators; parentheses; casts; and array creation and initializers whose parts are all of these (`new int[3]`, `{1, 2}`, `new Object[] {"a", null}`), each dimension given an int literal and the dimensions, multiplied up to the first 0 (past which nothing is allocated), coming to at most 65536, and none negative (`new int[65536]`, `new int[256][256]`, `new int[0][65537]`, `new int[65536][0]`; `new int[-1]`, `new int[65537]`, `new int[256][257]`, `new int[65537][0]`, `new int[0][0xFFFFFFFF]` (a hex or octal literal past `0x7FFFFFFF` is negative), `new int[1 + 1]` or `new int['a']` may throw, or are not read as a number, so they run code). A division or remainder counts only when its divisor, past parentheses and signs, is a nonzero integer or long literal or a floating one (`1 / 2`, `7 % -3L`, `1.0 / 0.0`); any other may be an integral division by zero and throw (`1 / 0`, `1 / (1 - 1)`, `1 / '\0'`), so it runs code and is no constant either. Anything else may observe the order, and a field initialized so keeps its order relative to every field of its static or instance group that is not inert: a read of any field (bare, through `this`, `super` or another object, a static of another type or a constant of one), a call (JDK ones such as `List.of(1)`, `Math.max(1, 2)` or `String.valueOf(3)` included), a `new` of anything but an array (`new ArrayList<>()`, `new Object()`), a lambda or method reference, a class literal, a switch expression, an `instanceof` test, an array access, a write (`++n`, `n += 1`, `(b = 5)`), handing out `this` (`Object self = this;`, `"v" + this`), and any other syntax, however deep in parentheses (`(Ids.next())`). A field is inert when it has no initializer or is a constant (`final` primitive or `String`, an interface's or annotation type's fields too, initialized from literals; `this`, `null`, a created array, a primitive's class literal in a concatenation, or a division that may be by zero make it no constant). The check reports no type, annotation, type-argument annotation or name order between such a pair, inside one declaration included, and the fixer keeps their order while it sorts the rest: `int zeta = Ids.next();` / `int beta = 2;` / `int alpha;` becomes `int alpha, zeta = Ids.next(), beta = 2;`. A chunk order still applies; when the kept order breaks it (`int zeta = Ids.next();` above `final String label = String.valueOf(2);`), the fixer returns a `SkipResult` (`cannot reorder fields: a field would move past another field whose initializer runs code or reads it, which could change the value read or written`). Over-pinned: a read or call that observes nothing still pins its field, a constant of another type (`Integer.MAX_VALUE`, `TokenTypes.IDENT`), which javac inlines, an own field the pair does not touch, and a JDK factory (`List.of()`, `new ArrayList<>()`) included |
| Enum constants out of alphabetical order | `ZETA,` above `ALPHA`, also when creating a constant runs code (`ZETA(Integer.parseInt("1"))`, a constructor registering each constant, `index = Csv.register(header);`, a body with a static initializer) or the enum's own code sees the order (`static final Level DEFAULT = values()[1];`, `compareTo(other) >= 0`, `EnumSet.of(ZETA, ALPHA)`, an `EnumMap`) | No (warning) | Reported as a warning (`Enum constant 'ALPHA' should appear before 'ZETA' (alphabetical order).`) whatever creating the constants runs or reads, and never auto-fixed: code anywhere, in this file or another, may depend on the declared order (a persisted or compared ordinal, a natural-order sort, an `EnumSet` range), so only a person can decide to change it. Constants sharing a line are still split onto lines of their own, in the order written (see the same-line rows) |
| Enum constants reading another constant | `ROOT(null), ELECTRONICS(ROOT), BOOKS(ROOT)`, `BOOKS(Category.ROOT)`, a constant body reading one, `ZED(ALPHA), ALPHA(null)` | No (warning) | Their order is reported like any other enum's (the row above), as a warning, and never auto-fixed. A constant reading a later one by bare name among its own arguments, which does not compile, is reported too, also as a warning (`Enum constant 'ZED' should appear after 'ALPHA' (dependency order).`); a read through the enum's name (`ZED(Shade.ALPHA)`) or from a body compiles and is not. Another type's constant (`Other.ROOT`), or one read through an object, is no read of the enum's own, nor is a lambda parameter, a constructor or body method parameter, a method named like a constant, or a `case` label (`case ALPHA ->` in a body's method) |
| Pinned pair where one reads the other by bare name ahead of its declaration | `int total = count + Integer.parseInt("1");` before `int count = 3;`, `int sum = alpha + beta;` before `int alpha = 1, beta = 2;`, a plain field reading a later anonymous-class field | No | The read does not compile as written, but the pin still holds the pair: a reorder there is the only one that could change a value, so it is never made. The check reports the dependency and the fixer returns a `SkipResult` (`cannot reorder fields: a field would move past another field whose initializer runs code or reads it, which could change the value read or written`, or `cannot reorder fields: they have a circular dependency` when two fields read different names of one declaration, as `int gamma = alpha;` and `int delta = beta;` before `int alpha = 1, beta = 2;`). With an inert target (`int count;`) the pair is not pinned and `count` moves up as for any dependency. A read through `this.` compiles, and is the row below |
| Field read while initializing, ahead of its declaration, in a form that compiles there | `int total = this.count * 2;` before `int count = 3;`, `Type.count` or `pkg.Type.count` in a static initializer, `int a = (b = 5) + 1;` before `int b = 2;`, `this.separator` in a lambda (`Stream.of(...).map(c -> this.separator + c)`), `String.valueOf(beta)` in an anonymous class's field or initializer block (nested ones too) before `final Object beta = new Object() {};`, or both in one declaration (`int total = this.count * 2, count = 3;`, also as a later name: `int alpha, total = this.count * 2;`) | No | The reader sees the later field's default, so moving that field first would change what it computes (`total` from 0 to 6). The fixer returns a `SkipResult` (`cannot reorder fields: a field would move to or above an earlier field whose initializer reads it, which would then see the default value`) for the whole static or instance group holding the pair, also when the pair is pinned as well. A lambda counts, since one called while initializing runs then. Reads of an earlier field or of the field itself (`int count = this.count + 1;`), of a field with no initializer, or of a constant (`final` primitive or `String`, `java.lang.String` too, initialized from literals) read the same either way and are reordered. A `final int` built by a call or a switch expression is no constant here. A member of another object or type (`other.count`, `super.count`, `System.out` beside an own `out = "o"`) and a method name (`this.size()` beside a later `size`) are no read of the later field, so nothing is reported; the read or call still pins the pair (see the row on pinned fields) when the later field is not inert. A name the initializer binds itself where its scope does not depend on a test is no read either: a lambda parameter, a method or constructor parameter of a local class, a local declared earlier in a block of a lambda, a switch arm or an anonymous class body's initializer block (`() -> { int rate; rate = 2; return rate; }` beside a later `int rate = ...`), and a for, catch or resource variable inside its own statement. Nor is a `case` label, which names a constant variable, whose value is inlined, or the selector's enum constant, nor a read through `Other.this` of an enclosing class's field (`Adapter.this.count` in a `Holder` declaring its own later `count`). A pattern variable is always taken for the field it is named like (`o instanceof String rate || rate.isEmpty()`, or a read after the `if` whose test bound it), since where it is in scope depends on how its test came out, which may only over-constrain the order |
| Initializer binding a name of a later field | `private final DoubleUnaryOperator discount = rate -> rate * 0.9;` before `private final double rate = initialRate();`, `() -> { int rate = 2; return rate; }`, `for (int rate : rates)`, `catch (Exception rate)` | Yes (order kept) | The name is the initializer's own, so it is no dependency to the field. A pattern variable (`o instanceof String rate && rate.isEmpty()`, `case Integer rate -> rate`) is not: it counts as a read of the field, so the field is kept ahead of the initializer, or moved there when it is inert. Both initializers run code, so the pair is pinned and keeps its order (moving `rate` first would call `initialRate()` while `discount` is still null). With `private final double rate = 1.5;`, a constant, the fields sort by type (`rate` first) |
| Dependency on a field in a later chunk | `final Object holder = new Object() { final long seed = counter; };` before `long counter;`, or `long counter = 5;` before `final long seed = counter + 1;` | No | No order satisfies both the chunk order and the dependency; the fixer returns a `SkipResult` (`cannot reorder fields: a field would have to follow a dependency in a later chunk`). This includes a chunk-0 plain field reading a non-final anon-class field while a non-final plain field reads a chunk-0 anon-class field, where each anon-class field waits on a plain field that waits across chunks |
| Multi-line initializers | Fields with anonymous class or lambda init | Yes | The declaration's full line span moves as a unit |
| Annotated fields | Fields with `@Deprecated` etc. above | Yes | Annotation lines move with their field |
| Nested generics in type | `Map<String, List<Integer>>` field | Yes | Reordered like any other type |
| Multi-line generic type | a generic type wrapped across lines (`Map<String,` / `Long> f;`) | Yes | The declaration's full line span moves as a unit |
| Circular dependencies | `A = B + 1; B = A + 1` | No | No order satisfies every dependency; the fixer returns a `SkipResult` (`cannot reorder fields: they have a circular dependency`) rather than emit a partial order |
| Cycle only between whole multi-variable declarations | `final Object a = new Object() {}, c = new Object() { final Object x = b; };` then `final Object b = a;` | No | `b` must sit between `a` and `c`, which share a declaration; the fixer returns a `SkipResult` (`cannot reorder fields: a dependency is bound in a multi-variable declaration`) |
| Anonymous class initializer | anon.class field must come after non-anon | Yes | Anon-class-init fields sort last within their chunk, after the inert plain fields of it (no initializer, or a constant): creating the anonymous class runs code, so a plain field with any other initializer is pinned to it and keeps its side (`final Thread worker = new Thread() {};` / `final Object note = "n";` / `final String label = "w";` becomes `label`, `worker`, `note`). Two anonymous-class fields are pinned to each other and keep their order. A plain field reading an anon-class field of the same chunk (directly or through other fields) only follows what it reads, so `a; ra; b; rb` (each plain reading one anon field) is kept. Reading an anon-class field of another chunk does not exempt it |
| Anon-class body reference | anon.class field's body mentions a sibling | Yes | A reference in the body's member initializers or initializer blocks runs while the field is initialized, so it orders like any dependency, unless the sibling is declared later with a value set at runtime (see the row on fields read while initializing). A reference in a method or a nested type is no dependency, but any method of the body may run while the field is initialized (called by its own initializer or by a superclass constructor), so the field keeps its place beside every non-inert field (see the row on pinned fields) |
| Anon-class read through a method | `new Object() { final String copy = read(); String read() { return label; } }` | Yes (order not adjusted) | No dependency is seen through a method call; the anonymous class keeps its order beside every non-inert field (see the row on pinned fields), so only an inert `label` is moved |
| Anon-class member shadowing a field | `new Object() { final String label = "inner"; final String copy = label; }` | Yes | A field the body declares (any declarator, static or instance, initialized or not) is what the body's own name refers to, so it is not a read of the outer field. A nested anon class's fields shadow only inside it, while constructor arguments and `Outer.this.label` still read the outer field |
| Local, lambda parameter or method in an anon body named like a field | `new Object() { final Function<String, String> copy = label -> label; }`, `{ final var label = "local"; System.out.println(label); }`, `final String copy = label();` | Yes | A lambda parameter, a local or a method's name is the body's own, so it is no read of the outer field, and the anonymous-class order applies alone (`label` moves above the field) |
| Multi-variable declaration mixing anon-class and plain initializers | `final Object task = new Thread() {}, label = "w";` beside another field | No | The check orders the declarators individually. Any group containing such a declaration is refused; the fixer returns a `SkipResult` (`cannot reorder fields: a multi-variable declaration mixes anonymous class and plain initializers`). Alone in its group it is the initialized multi-var skip below |
| Multi-variable declaration mixing anon-class readers and free fields | `final int p = 1, q = anon.hashCode();` after `final Object anon = new Object() {};` | No | `p` must precede `anon` while `q` must follow it, which only splitting the declaration could satisfy; the fixer returns a `SkipResult` (`cannot reorder fields: a multi-variable declaration mixes names that read an anonymous class field and names that must precede one`) |
| Multi-variable declaration with an interior comment | `String zebra, /* c */ alpha;` or a comment on a continuation line | No | Reordering the names would drop the comment; the fixer returns a `SkipResult` (`cannot reorder fields: a multi-variable declaration contains a comment`) |
| Initialized multi-variable declaration | `int beta = 1, alpha = 2;`, `final int b, a = 1;` | Yes | Each declarator moves with its initializer: in a `final` declaration those with a value first, then by name, each after the names it reads (`int alpha = 1, beta = alpha;` stays as is) |
| Initialized multi-variable declaration with a declarator spanning lines | `final Thread beta = new Thread() {` / `}, alpha = new Thread() {` / `};`, or an initializer wrapped onto the next line | No | The rebuild lists the declarators on one line; the fixer returns a `SkipResult` (`cannot reorder fields: a multi-variable declaration with initialized names has a declarator spanning lines`) |
| Multi-variable declaration placed among other fields | `long beta;` then `long alpha, zeta;` | Yes | A declaration sits among the other fields by its first name only, so `long alpha, zeta;` before `long beta;` is in order and the reverse is fixed (`long alpha, beta, zeta;`). Its own names are still checked against each other (`long alpha, zeta, beta;` reports `beta`), and a dependency between two declarations still decides their order whatever their first names |
| Initialized same-key fields | `int beta = 2;` then `int alpha = 1;` | Yes | Merged when neither reads a field, declarators in the order above (`int alpha = 1, beta = 2;`) |
| Multi-variable declaration with a C-style array declarator | `int y[], x;` | No | The name-only rebuild emits the shared type prefix plus the names, carrying no per-declarator suffix, so reordering would drop a declarator's own `[]` and silently retype it; the fixer returns a `SkipResult` (`cannot reorder fields: a declarator carries its own C-style array brackets`) |
| Multi-variable secondary-name dependency | `int z;` then `int a = y + 1;` then `int x, y;` | Yes | The declaration holding the read name moves as a whole ahead of the reader (`int x, y;` / `int a = y + 1;` / `int z;`). A cycle through a multi-variable declaration is still refused with `cannot reorder fields: a dependency is bound in a multi-variable declaration` (see the row on a cycle between whole multi-variable declarations) |
| Field ordered past a secondary name | `final Object task = new Object() {};` then `final String label = "w", note = String.valueOf(1);` | No | The check orders declarators, the rebuild orders whole declarations: `task` must follow `label` but stay ahead of `note`, which it is pinned to, so it would have to sit between two names of one declaration; separating them needs a declaration split, so the fixer returns a `SkipResult` (`cannot reorder fields: a field would move past a name bound in a multi-variable declaration`) |
| Leading block comment without star continuations | `/* block\n\tcontinuing line without a star\n\t*/\n\tString zebra;` | Yes | The whole comment travels with the field it sits above, whether or not its middle lines carry a star |
| Leading comment owned by no field | a comment separated from the field below it by a blank line | No | The rebuild emits only the entries' own lines, so a comment in the span that no field owns would be deleted; claiming a `*/` without its opener would instead move the closer above the opener and comment the next field out while still compiling. The fixer returns a `SkipResult` (`cannot reorder fields: a comment between them belongs to no field`) |
| Field sharing a line with other code | `private String name; private int count;`, `private int alpha; }`, `}; final String label = "w";`, `ALPHA; static final int ZETA = 1;`, a text block closing on the line of the next field, or a block comment the field's last line leaves open (`private int count; /* retries,`) or its first line closes (`more */ int alpha;`) | No | The rebuild moves whole lines, which would duplicate or carry off the other code, or move a field into the middle of a comment; a comment that opens on its own line above the field and closes before it is the field's own and does not count, unless a blank line inside the comment separates its opener from the field; the fixer returns a `SkipResult` (`cannot reorder fields: a field shares a line with other code`) for any group containing such a field. A shared line in the other static/instance group does not block the fix |
| Wrapped declaration beside a mergeable field | `private long delay = 60` / `* 1000;` beside `private long timeout;` | Yes (reorder only) | Only a declaration that starts on its last line, with no declarator spanning lines, is merged, so a wrapped one is reordered but never consolidated. `FieldConsolidationFixer` merges it onto one line (`private long delay = 60 * 1000, timeout;`) |
| Field whose initializer reads another field, in a group being reordered | `int alpha = beta + 1;` beside another `int` field | Yes (reorder only) | Moved but never merged here, and neither is a field merged into it. `FieldConsolidationFixer` merges such fields, in dependency order |
| Comment on a mergeable field | a comment on a later same-type, same-annotation field's annotation line, or ahead of its type (`/* package */ int beta;`, `@Deprecated // why` above it) | Yes | Merged, the comment moved above the merged declaration and joined with any other moved one into one line comment in source order, as `FieldConsolidationFixer` moves them (`// why` / `@Deprecated` / `String body, title;`). A comment the first field repeats word for word is not repeated. Any comment on the first field stays where it is (`/* px */ int alpha, beta;`, `// in pixels` or `/**/` above `int height, width;`, `@Deprecated // why` above `String body, title;`) |
| Comment that blocks a merge | a comment on a line of its own above the later field (`/* keep me */` or `// keep me` above `String zebra;`, which `String alpha;` sorts ahead of), a comment on either field past its type: among its names, before its `;` or after it (`int beta /* px */;`, `int alpha; /* px */`), a block comment one of its lines leaves open, or a doc comment on either field that the other does not repeat (`/** px */`, `/***/` or `/// px` above it, or `@Deprecated /** px */ private int height;`) | Yes (reorder only) | The merged line keeps only the later field's names, so a comment among them would be dropped, and a moved comment has to fit on one line. javac would give a doc comment to every merged name |
| Tool directive on a comment that would move | `NOSONAR`, `NOPMD`, `$NON-NLS-`, `CHECKSTYLE`, `language=`, `noinspection`, `@formatter:` or `spotless:` in a comment on a later field's leading or annotation line, or ahead of its type (`@Deprecated // NOSONAR` above it, `/* NOSONAR */ int zeta;`) | Yes (reorder only) | Moved onto a line of its own, the directive would stop covering the field it was written for. One the kept field repeats word for word does not move, so the merge goes ahead (`@Deprecated // NOSONAR` / `private int alpha, zeta;`). The match is case-sensitive, the same rule `FieldConsolidationFixer` applies |
| Tool directive on the declaration line of the field the others would merge into | `/* NOSONAR */ private int alpha;` sorted ahead of `private int zeta;` | Yes (reorder only) | Merged, the later names would join the directive's line and it would cover them too, so the fields are only reordered (`/* NOSONAR */ private int alpha;` / `private int zeta;`). A directive trailing that field (`private int alpha; // NOSONAR`) already blocks the merge as a comment past its type does (see the row on comments that block a merge) |
| Tool directive leading the field the others would merge into | `//noinspection unused` above `int alpha;`, which `int beta;` and `int zeta;` sort after; also a tool directive on a line of its own above it (`// language=SQL`, `// NOSONAR`); one switching a tool off or on or counting lines (`// @formatter:off`, `// CHECKSTYLE IGNORE X FOR NEXT 1 LINES`) is the range-directive row instead | Yes (reorder only) | Such a directive may act on the declaration or lines after it, so names merged into that declaration would fall under it too; the fields are reordered but none is merged into it (`//noinspection unused` / `int alpha;` / `int beta, zeta;`). Which directives lead a declaration is one rule shared with FieldConsolidation, whose check puts such a declaration in no run: a `//noinspection` counts wherever it leads the declaration, an annotation line included (`@Deprecated //noinspection unused`), trailing the line above, or across blank lines and other comments; any other directive only on a line of its own, above the declaration or between its annotations and its type, or starting on one and spanning lines, closing on the name's line at the latest (`/* NOSONAR` above `*/ int alpha;`), so one trailing an annotation line (`@Deprecated // NOSONAR`) or the line above acts on that line and the merge goes ahead, as does one ahead of an annotation on its line (`/* NOSONAR */ @Deprecated`), while one ahead of the type (`/* NOSONAR */ int alpha`) is the previous row. The match is case-sensitive, so `// NoInspection` and `// Language=SQL` are plain comments |
| Tool directive leading a field from outside its lines | `//noinspection unused`, a blank line, then `int zeta;` above `int alpha;`, or `final int limit = 1; //noinspection unused` above `int zeta;` and `int alpha;` | No | The directive is not one of the field's own comment lines, so it stays where it is while the fields below it move, and would then lead another field (with `// language=SQL`, inject into another field's literal).
