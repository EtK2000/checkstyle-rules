# MultilineCallFormattingCheck auto-fix coverage

The fixer handles three families of multi-line call/argument layout violations, reusing the
check's own classification so it never disagrees with the check:

1. **Collapsible `put`**: joins a split `new JSONObject().put(k, simpleValue)` onto one line.
2. **Closing-paren moves**: push a call's `)` onto its own line, or pull it up to stack with an
   inline block's brace / rejoin a single-line ternary. Applied only when the moved paren is the
   call's sole violation (a call that also has an opening-paren or shared-line violation is handled
   by family 3 instead).
3. **Opening-paren / argument moves**: split a plain first argument off the `(` line, or pull an
   inline-block or ternary argument up onto the `(` line and re-stack the `)`, collapsing the whole
   call onto one line when the one-line form fits within 120 columns.

Every rewrite re-indents the affected span to the project's canonical layout regardless of the input
indentation; ternary-internal and shared-line argument layouts are re-laid-out in full. All layout
messages this check emits have a fixer. See the per-message table below.

| Message | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| `multiline.put.collapsible` | Split `new JSONObject().put(k, simpleValue)`, collapsed form ≤120 chars | Yes | Joins the whole enclosing statement onto one line, not just the `.put` sub-call, so the enclosing call's closing paren is not left dangling |
| `multiline.put.collapsible` / closing pull-up | A `//` line comment sits on a line that would be joined (before the last) | No | Joining (collapse, or a closing-paren pull-up) would pull the comment inline and swallow the rest |
| `multiline.put.collapsible` | Reported location no longer resolves to a collapsible `put` (stale/mismatch) | No | The reported span is stale (out of range or single-line after a prior edit) |
| `multiline.args.on.closing.paren` | Argument on the closing paren line, and it is the call's only violation | Yes | Re-emits the whole argument list: collapses the call onto one line when it fits within 120 columns (per CLAUDE.md "prefer single line"), else each argument (itself collapsed onto one line, so a nested multi-line plain call becomes one line) on its own line with `)` (and any trailing `;`/`{`/chain) on its own line. Falls back to the layout-preserving push-down when an argument needs its own opening-line shape (an inline-block or ternary configuration), a `//` comment would be swallowed, or the call spans a text block / multi-line comment |
| `multiline.lambda.not.on.closing.paren` | Inline block closing brace/paren not on the closing paren line (sole) | Yes | Pulls `)` up to stack with the inline block's `}`/`)` (`});`) |
| `multiline.ternary.not.on.closing.paren` | Single-line ternary closing paren not on the same line (sole) | Yes | Pulls `)` up onto the single-line ternary's value line |
| `multiline.args.on.closing.paren` (etc.) | Closing (or opening) violation on a call that ALSO has a shared-line violation | Yes | The closing/opening move defers, and the shared-line arm re-emits the whole argument list (resolving all coordinates of that call in one rewrite) |
| `multiline.args.on.opening.paren` | First argument on the opening paren line, and it is the call's only violation | Yes | Re-emits the whole argument list: collapses the call onto one line when it fits within 120 columns (per CLAUDE.md "prefer single line"), else each argument (itself collapsed onto one line, so a nested multi-line plain call becomes one line) on its own line at the base indent + one continuation level. Falls back to the layout-preserving split when an argument needs its own opening-line shape (an inline-block or ternary configuration), a `//` comment would be swallowed, or the call spans a text block / multi-line comment |
| `multiline.lambda.not.on.opening.paren` | Inline block argument not starting on the opening paren line (and the pull-up is feasible) | Yes | Pulls the block up onto the `(` line and re-stacks the `)`; collapses to one line when the single-line value fits ≤120. The check emits this only when the pull-up is feasible (see the two "not flagged" rows below); a `//` on the value's own first line (the kept head line, not a joined line) does not block it and is preserved on the pulled-up value |
| `multiline.ternary.not.on.opening.paren` | Ternary condition not on the opening paren line | Yes | Pulls the condition up onto the `(` line, keeping `?`/`:` and the `)` on their own lines. A single-line ternary whose one-line form fits collapses onto one line; when it exceeds 120 it is re-laid-out multi-line (condition on the `(` line, `?`/`:` each on their own line) rather than skipped |
| `multiline.lambda.not.on.opening.paren` | Inline block value is `java.util.List.of` etc. (fully-qualified receiver) | Deferred | Skip while the receiver is a raw FQN, so `PreferImportFixer` shortens it first; the pull-up runs on a later pass |
| `multiline.lambda.not.on.opening.paren` (suppressed) | Inline-block single-line value whose collapsed one-line form would exceed 120 columns | n/a | Not flagged: the check suppresses the opening violation because the only clean shape (the one-line collapse) would exceed 120 and the fixer will not re-flow the value's chain. If the value also lands on the `)` line, the closing violation still fires and is fixed (the `)` moves to its own line; the key stays) |
| `multiline.lambda.not.on.opening.paren` (suppressed) | Inline-block multi-line value with a `//` line comment on a key line the pull-up would join (between the `(` line and the value's first line) | n/a | Not flagged: the check suppresses the opening violation because joining the head lines would pull the comment inline and swallow the value. A closing violation on the same call still fires and is fixed |
| `multiline.postdelayed.one.line` | `Handler.postDelayed(inlineBlock, delay)` whose first arg is a braced lambda with a single *expression*-statement body that collapses within 120 columns | Yes | Unwraps the lambda braces and collapses the whole call onto one line (`handler.postDelayed(() -> stmt, delay);`) |
| `multiline.lambda.not.on.opening/closing.paren` | `Handler.postDelayed(inlineBlock, delay)` that cannot be one-lined: an anonymous-class first arg, a non-expression lambda body (`return`/`if`/var/`throw`/...), a multi-statement body, or a collapsed form > 120 | Yes | The inline block opens on the `(` line, its body stays multi-line, and `}, delay);` stacks on one line after the body. (postDelayed is intercepted before the generic opening/closing moves so it owns this canonical) |
| `multiline.postdelayed.one.line` / `.lambda.*` | `Handler.postDelayed(...)` whose body span carries a `//` comment on a joined line | No | Joining the body would pull the comment inline and swallow the rest |
| `multiline.postdelayed.one.line` / `.lambda.*` | `Handler.postDelayed(...)` whose body spans a text block or multi-line block comment | No | A multi-line literal in the body cannot be collapsed onto one line |
| `multiline.lambda.not.on.opening.paren` / `.ternary.not.on.opening.paren` | A `//` line comment on the `(` line (inline block; the check's feasibility scan excludes the `(` line, so the violation still fires) or on a line a ternary pull-up would join | No | Joining would pull the comment inline and swallow the rest |
| `multiline.lambda.not.on.opening.paren` | The pulled-up argument's interior spans a text block or multi-line block comment | Yes | Re-emits with the interior re-indented structurally while any line that begins inside a text block or block comment is kept byte-verbatim (its significant whitespace is never touched). When the closing-delimiter line also carries the call's closing bracket run (`text"""; });`), the delimiter (with any statement terminator) stays verbatim and the `});` run drops to its own line at the call's brace depth. A multi-line block-comment interior is handled identically |
| `multiline.args.on.opening.paren` / `.closing.paren` | Reported coordinate is stale after a prior same-file edit (line out of range, or `(`/`)` no longer at the reported column) | No | The push-down / pull-up bails rather than edit a shifted (stale) line |
| `multiline.args.shared.line` | Multiple arguments sharing a line (call `METHOD_CALL`/`LITERAL_NEW`/`SUPER_CTOR_CALL`, or def `METHOD_DEF`/`CTOR_DEF`) | Yes | Re-emits the whole list: collapsed onto one line when the call/def fits within 120 columns (per CLAUDE.md "prefer single line"), else `(`/`)` on their own lines with each argument/parameter (itself collapsed onto one line) on its own line at +2 tabs; also resolves a co-occurring opening/closing violation on the same call. Not split at commas inside generics/strings/nested calls (sliced at AST arg boundaries) |
| `multiline.args.shared.line` | A trailing `//` comment on a non-final argument (the next line begins with the leading `,`) | Yes | Re-emits multi-line (never one line); the `,` is hoisted ahead of the comment so the argument keeps its comment on its own line (`a // note` then `, b` becomes `a, // note` then `b`) |
| `multiline.args.shared.line` | A `//` comment mid-argument (code before the `//` on its line, more of the argument on later lines) | Yes | The argument is emitted verbatim (its own source lines, never joined) so the comment is kept, while sibling arguments still collapse/split around it |
| `multiline.args.shared.line` | A `//` comment that leads a segment (it trailed the previous `,`, or sits on its own line before the argument) | Yes | The comment is lifted back onto the previous argument's line (after its `,`, or onto the `(` head for the first segment) and the argument splits onto its own line (`a, // note` then `b, c` becomes `a, // note` / `b,` / `c`). When the argument is emitted verbatim (text block / braced block), the lifted comment's own source line is dropped so it is not also re-emitted inside the block; only the first of several leading comments is lifted, the rest stay verbatim |
| `multiline.args.shared.line` | A `//` comment on the final argument (nothing joins behind it) | Yes | Preserved and does NOT block: the whole-list re-emission is forced to the multi-line shape (a one-liner would bury the `)` behind the comment), each argument on its own line with the comment kept |
| `multiline.args.shared.line` | An argument spans a text block or multi-line block comment | Yes | Re-emits the list to the multi-line shape; the spanning argument is emitted verbatim (never collapsed onto one line) so its significant text-block/comment whitespace is preserved, while sibling plain arguments still collapse as usual |
| `multiline.args.shared.line` | An argument contains a multi-line braced block (a lambda, anonymous-class, or switch body) | Yes | Re-emits the list to the multi-line shape; the braced-block argument is emitted verbatim (never tight-collapsed onto one line, which would cram the body and usually exceed 120), while sibling plain arguments still collapse as usual. A braced block already written on one line still collapses |
| `multiline.args.shared.line` | Reported coordinate is stale after a prior same-pass edit (a `(`/`,`/`)` boundary no longer at its reported column) | No | The whole-list re-emission bails rather than slice a shifted (stale) span |
| `multiline.ternary.question.wrong.line` | Ternary `?` not on the line after the condition | Yes | Re-emits the whole ternary: condition on the `(` line, `?`-branch then `:`-branch each on their own line, `)` on its own line; also resolves a co-occurring `not.on.opening.paren` / closing violation on the same ternary. Each branch is collapsed onto one line |
| `multiline.ternary.colon.wrong.line` | Ternary `:` not on the line after the true branch | Yes | Same whole-ternary re-emission as `question.wrong.line` |
| `multiline.ternary.*.wrong.line` | A `//` comment sits on a non-final line of a segment the re-layout would collapse | No | Joining later content behind the comment would swallow it. A comment on a segment's last line (e.g. a trailing comment on the condition) is preserved and does NOT block |
| `multiline.ternary.*.wrong.line` | A branch spans a text block or multi-line block comment | Yes | Re-emits the ternary to its canonical shape; a branch that spans a text block or block comment is emitted verbatim (never collapsed) so its significant whitespace is preserved, while a plain branch still collapses onto its `?`/`:` line |
| `multiline.ternary.*.wrong.line` | A long branch pushes the canonical `? <branch>` / `: <branch>` line past 120 columns | Yes | Still fixed: the correct multi-line shape beats the pre-existing broken layout, and no fixer in the pipeline re-wraps an over-long branch |

## Known unsound

| Pattern | Reason |
| --- | --- |
| Reformatted line containing a supplementary character before the anchor token | `SpanReformat.pointsAt` indexes with `charAt(col)` where `col` is a CODE-POINT column, so a non-BMP character earlier on the line shifts the read. `JavaTernaryReformatter`, `JavaPostDelayedReformatter` and `JavaArgListReformatter` all gate on it, and because it is a VALIDATING guard the shifted read normally fails to match the expected `?`/`:`/`)`/`{`/`}` and the caller returns `CannotReformat(Reason.STALE)`, which is a safe refusal. The residual risk is a coincidental match, where the shifted index happens to land on an identical character and the reformat proceeds against the wrong token. Fix is `LineText.charIndexOfColumn` inside `pointsAt`, which also removes the refusals |
