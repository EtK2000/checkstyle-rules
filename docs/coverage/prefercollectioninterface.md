# PreferCollectionInterfaceCheck auto-fix coverage

Replaces a concrete collection type in a method or constructor signature with its interface
(e.g. `ArrayList` to `List`).

Every concrete collection type in a signature is reported. It is reported as an **error**, and so
auto-fixed, only when the rewrite is provably contained in this compilation unit; otherwise as a
**warning**, which the fix pipeline never applies. A rewrite that would be outright wrong is not
reported at all.

The two tiers ask different questions, because a parameter and a return type break differently:

| Position | What breaks | Auto-fixed when |
| --- | --- | --- |
| Parameter | An override in a file this run cannot see. Without `@Override` the two silently stop being a pair and dispatch changes | Nothing outside this file can override the member: it is a constructor, or `private`, or its declaring type is an enum, record or `final` class, or a type nothing can name to extend (an enum constant body, an anonymous class, a local class). `static` and `final` are NOT enough on their own: a subclass in a file this run cannot see still declares a same-named member, and the widened signature turns its legal overload into an illegal override of a `final` method, or makes a `static` one hide rather than overload |
| Return type | A caller in a file this run cannot see. Widening keeps every unseen override legal, so overridability is the wrong question here | Nothing outside this file can name the member to call it (`private`, or a declaring type that is an enum constant body, an anonymous class, or a local class that is not itself `final`, an enum or a record) AND every call in this file still compiles and still binds. Each call's consuming position is decided by the same whitelist the parameter row uses, so a result assigned to a concrete-typed target, passed where the interface is rejected, or read through a method the interface does not declare holds the return type back. A result that survives only because ANOTHER return type widens is refused rather than chased, and a call reached through a method reference is refused, since neither names what consumes it |
| Record component | Both at once: the component types the canonical constructor's parameter and the accessor's return, and JLS 8.10.3 forces the two to stay identical. It therefore takes the return-type rule, applied to the record itself rather than to a member | Nothing outside this file can name the RECORD (`private`, or declared inside an enum constant body, an anonymous class, or a method body) AND every accessor call in this file accepts the interface, by the same rule as a return type. A top-level record is the most reachable shape there is, so its components are reported and never auto-fixed. One answer decides the component and its explicit accessor together, since the two must stay identical |

`static` and `final` stop a member being overridden but do nothing to stop it being called, which is
why they decide neither tier on their own.

A parameter is additionally held back from the error tier when an overload of the same name is
reachable that could take a call of its arity (a variable-arity overload included, or a
variable-arity parameter beside a fixed-arity overload), since widening makes the signature
applicable to calls that used to bind to that overload and resolution then picks whichever is more
specific, and when its own body only survives widening because it is returned through a return type
moving to the same interface while that return type is itself held back from the error tier. When
that return type is auto-fixed too, both move together.

The owner's visibility decides nothing in either tier: a public subtype in this package re-exports
the member, and any other package may then extend that subtype, so a package-private or `private`
nested owner is no protection.

A record component and its explicit accessor are rewritten in ONE edit, anchored on the component,
and if either half cannot be rewritten neither is. JLS 8.10.3 forces the
accessor's return type to be identical to its component's, so a half-rewrite does not compile
(`return type of accessor method items() must match the type of record component items`). Every
refusal below that names the pair is that rule: it costs the component's fix as well as the
accessor's.

## Not flagged by check (correct behavior, not a limitation)

| Pattern | Reason |
| --- | --- |
| Parameter list whose rewrite would duplicate another overload (`dump(List<String>)` alongside `dump(ArrayList<String>)`) | Only the parameter list is exempted; a return type cannot create an overload collision, so it is still flagged on both declarations (the sole exception is an override of a supertype outside this file, see below). Replacing the concrete type would make the two signatures identical and the file would stop compiling. Overloads are compared on their erased parameter types, positionally, which is the identity the compiler uses. A varargs parameter erases to an array, so `dump(ArrayList<String>...)` beside `dump(List<String>)` is still flagged; a type variable erases to its bound, and a same-file type is identified by where it is declared, so `Box` and `Outer.Box` are one type rather than two |
| Method whose rewrite would duplicate an overload declared on a same-file supertype or subtype | The two signatures would become an override or a hide instead of an overload, silently rebinding existing calls to the other method, or fail to compile outright when the access differs. Only the type itself and its subtypes can see the member, so those and their supertype chains are searched; sibling types are excluded, since neither inherits the other's members. A private member is skipped only in a supertype, where it is not inherited: a subtype declaring one whose erasure matches an inherited method is a weaker-access compile error, not an overload. Anonymous class bodies, enum constant bodies and local classes are linked to their supertypes too. Constructors are never inherited, so only the declaring body is searched. A static interface method is not counted, since an implementor does not inherit it. Two members whose erased parameter types are ALREADY identical are an override or hide pair rather than a collision the rewrite would create, so both are still flagged and both are rewritten, which preserves the relation |
| Method whose rewrite would duplicate an overload inherited from a supertype in another file | The supertype is resolved from the classpath and its methods compared on their erased parameter types, so the collision is caught even with no AST for it |
| Method that overrides one declared by a supertype outside this file (e.g. an override of a JDK method) | The supertype pins the signature: the parameters cannot change without breaking the override, the return type cannot widen without breaking covariance, and the supertype is not visible to be rewritten alongside it. This is the one case where the return type is exempted as well as the parameter list. The question is asked with the method's CURRENT erasure, so a method that would merely COLLIDE with an inherited overload once rewritten, rather than already overriding one, keeps its return-type violation |
| Record component whose rewrite would give the canonical constructor an explicit constructor's erasure | The component list is both the canonical constructor's parameters and the accessors' return types, so rewriting it would produce two constructors with one erasure |
| Type nested inside another type's type arguments (`Map<String, ArrayList<Integer>>`) | Generics are invariant, so this is a substitution rather than a widening: `Map<String, List<Integer>>` is not a supertype of `Map<String, ArrayList<Integer>>` and every call site breaks, including ones in this same file that the fix does not touch. The one position that genuinely widens is a `? extends` bound on a parameter, which is still flagged, and only when every enclosing type-argument level was itself entered through such a bound: an invariant level anywhere above it (`List<Set<? extends ArrayList<X>>>`) makes the rewrite a substitution again. The same bound on a return type narrows what the caller may assign, a record component is both at once, and a `? super` bound narrows everywhere, since raising its lower bound accepts fewer arguments |
| Parameter the body uses somewhere that demands the concrete type (`values.ensureCapacity(10)`, `items = values`, `values::trimToSize`) | Widening the parameter changes what every use of it may do, so each use is decided against its own target: a call the interface does not declare, any method reference (`values::clear` included, though the interface declares it), an initializer of a concrete-typed variable, an assignment to another variable or field whatever that target's type, an argument the callee's parameter would reject, or a return the enclosing return type would reject. Positions that read the value through `Object` alone (concatenation, equality, `instanceof`, an enhanced `for`) always survive, as does writing through the name itself, since the target there is the declaration being widened. A target this file declares, or a callee the classpath cannot resolve, refuses rather than guesses. The refusal is per parameter, so a second parameter on the same method is still flagged. An array or varargs parameter widens its ELEMENT type, so `length` and indexing survive and it is the uses on an element that must hold. A record component is checked against every body in the record, since it is the canonical constructor's parameter and the accessor's return type at once |
| Simple name that this file declares as a type, even when an import gives the same spelling a collection (`Stack`, `Properties`) | Java resolves a type declared in this compilation unit ahead of an import, so resolving against the classpath would read the user's own type as a collection and rebind the signature to an unrelated one. Local classes and inherited member types count as declared |
| Signature whose replacement name is already bound in this file (`class List` of its own, or `import java.awt.List`) | The fix writes the bare simple name and adds a `java.util` import, so a file that already binds that name would have every other use of it silently rebound to `java.util`, or would stop compiling outright on the duplicate |
| Annotation name or annotation member name appearing inside a signature type (`@Ann(ArrayList = "x")`) | Neither is a type in the signature, so resolving them would rewrite the annotation itself. A type-use annotation is a sibling of the type it annotates rather than its parent, so skipping the subtree cannot hide an annotated type argument |

## Missed by check (unintended)

Nothing is reported, so neither the warning tier nor the fixer ever sees these. Unlike the rows
above, the silence is not a decision.

| Pattern | Reason |
| --- | --- |
| Array-typed record component whose explicit accessor returns it bare (`record R(ArrayList<String>[] items) { public ArrayList<String>[] items() { return items; } }`) | An array component's uses are only accepted for indexing and `.length`, so a bare `return` refuses the component before it is weighed against the accessor's type, and the component and its accessor are skipped together. The non-array form is flagged |

## Not supported

| Pattern | Reason |
| --- | --- |
| Column out of range (negative, or at/past end of line) | The violation column is outside the line's content |
| No identifier at the violation column | The column does not point at a Java identifier character |
| Reported position that no longer names a type | An edit earlier in this pass moved the text under the violation (changed the line count, or shifted the column onto another token or into the middle of a name), so the position describes text the check never saw. Reported as `cannot replace the type: the reported position no longer names a type` |
| Class not resolvable | The class can't be resolved (missing from the classpath, or an unresolvable name) |
| Class is not a standard collection | The resolved class is an interface, abstract, ambiguous, or not in the supported set |
| Buffer that does not parse and spells `record` outside comments and literals | With no parse nothing tells a record component or accessor apart from an ordinary parameter or return type, and taking the line-local path there would rewrite one half of a pair alone, which does not compile. Checkstyle reports a parse error and runs no check on a file that does not parse, so the buffer got that way from an earlier fix in this pass. The word inside a comment or a string does not refuse; an identifier spelled `record` does. A buffer that spells it nowhere has no pair to break and still takes the line-local path. Reported as `cannot replace the type: a record component and its accessor cannot be rewritten as one edit` |
| Position on a qualifier segment of a record component's or accessor's type (the `util` of `java.util.ArrayList`) | A pair is built only when the position names the type itself, the last segment of the chain, so a segment left of it is recognised as a record position without producing a pair, and the line-local path would rewrite the segment alone. The check logs at the chain's last identifier and never at a segment, so this is reachable only from a position an earlier edit in this pass invalidated, or from a synthetic one. Reported as `cannot replace the type: a record component and its accessor cannot be rewritten as one edit` |
| Component or accessor name interrupted by a comment (`java./*note*/util.ArrayList`) | The rewrite replaces everything between the name's two ends with the interface name, so anything in there that is not the name would be deleted. Whitespace is what makes a qualified name broken across lines one span, so only whitespace is tolerated; a comment, or any other non-whitespace, refuses. The same guard refuses a span whose columns fall outside the lines it covers. Reported as `cannot replace the type: a record component and its accessor cannot be rewritten as one edit` |
| Component and accessor spellings that do not resolve to the same interface | Each half is resolved on its own, from its spelling through this file's package and imports, because the two need not be spelled alike (`ArrayList` against `java.util.ArrayList`). One replacement name is written into both halves, so a half that resolves to no concrete collection, or two halves that resolve to different interfaces, leave no name that fits both. Reported as `cannot replace the type: a record component and its accessor cannot be rewritten as one edit` |
| Violation reported on the accessor half of a record pair | Not a failure: the pair is one edit anchored on the component, so the accessor's violation defers and the component's carries the rewrite. Both halves are still checked for an intact span and a resolvable interface first, so an accessor violation reports the refusal reason when there is one rather than the deferral. Reported as `cannot replace the type: the record accessor is rewritten with its component` |

## Known unsound

Unlike the rows above, these are not skips: the check flags and the fixer rewrites, and the result may not compile.

| Pattern | Reason |
| --- | --- |
| Method whose rewrite would duplicate an overload inherited from a supertype that is neither in this file nor loadable | The collision is decided against the supertype's declared methods, which needs either an AST here or a class the checkstyle run can load. With neither there is nothing to compare against, so the rewrite is applied blind. This is the DEFAULT for a supertype declared in a sibling source file, not an edge case: the plugin puts only the `compileClasspath` and `testCompileClasspath` configurations on the checkstyle configuration, never the main source set's output, so a same-package sibling never loads. Adding the output directory would not fix it, because the guard would then be sound or unsound depending on whether a previous build left stale classes on disk. The exposure is confined to the error tier |
| Override pair where only one half is refused | Two members whose erased parameter types already match are treated as an override pair the rewrite preserves, on the premise that both halves are rewritten together. A refusal that applies to only one of them (its body needs the concrete type, it has no body to inspect, or only one half has a call site that holds it back) breaks that premise: the other half is rewritten alone, so the override silently becomes an overload, or an abstract method is left unimplemented |
| `? extends` bound on a parameter whose body uses the element's concrete API (`items.get(0).ensureCapacity(10)`) | The use-site check asks what the body calls on the parameter itself, which is the position the rewrite changes. Widening the bound also changes what the elements are known to be, and tracking that needs the type of an arbitrary expression rather than one declared name |
| Record component whose accessor a supertype already declares | The accessor's return type has to stay identical to its component (JLS 8.10.3), so a supertype that pins the accessor pins the component with it. A same-file supertype is left to the ordinary walk, which flags and rewrites both halves together, unless that declaration is itself held back from the error tier (a caller outside this file can reach it, a call in this file holds it back, or it overrides a method from the classpath), in which case the component is not reported; the transitive closure is searched, since the accessor may sit on an interface the record only reaches through another. A supertype this run cannot resolve, cannot load, or whose members cannot be read is refused outright, since nothing here can show it does not declare the accessor and no violation would ever be reported against it |
| Signature naming a nested classpath type (`Map.Entry`) whose override or collision guard should have caught it | A nested classpath type never matches in the override and collision guards, so they report no override and the rewrite can break one |
| Receiver call where the concrete type declares a narrower overload the interface lacks (`contains(String)` beside `Collection.contains(Object)`) | Overloads are paired by positional assignability so a bounded type variable still matches, which cannot be told apart from a genuinely more specific overload. The call silently rebinds to the interface's general form. The pairing also stops at the first match, so which overload supplies the return-type comparison depends on unspecified reflection order |
| Method whose classpath supertype loads but whose members cannot be read | An unreadable supertype is treated as declaring no such method, so the signature it pins is rewritten. Only the record-accessor path tells the two apart. The exposure is confined to the error tier |
| Array return type or array record component | The tier is decided against the ELEMENT type, so an array declaration is judged exactly as the non-array one and auto-fixed on the same conditions. Every consuming position is therefore weighed for `ArrayList` when the value is an `ArrayList[]`, and those are not the same question: a target, an argument or a return is asked whether it accepts `java.util.List` while what reaches it is a `List<String>[]`. For the cases we know of the direction is conservative, costing coverage rather than correctness: an `Object[]` or varargs parameter takes the array but not the element type, so the argument check finds no candidate and refuses |
| Type that no other file can subclass but that the tier still treats as extendable (a `sealed` type, or a class whose constructors are all `private`) | Costs coverage, never correctness: the member is reported as a warning rather than auto-fixed. Recovering it needs the same-file subtype closure, because both shapes are defeated by a same-file public subtype that re-exports the member, so neither can be decided from the declaration alone |
| Column drifted onto a nested type argument (`Map<String, ArrayList<String>>`) | The check never reports a type argument or a lower bound, but the fixer accepts one when a column an earlier fix in the same pass shifted lands on it, and rewrites the nested name. That produces the invariant substitution `Map<String, List<String>>` that the "Not flagged" table exists to prevent. `? super ArrayList` has the same shape. It is unverified whether a shifted column can land back inside a signature type |
| Column drifted onto a lambda or catch parameter (`(ArrayList list) -> ...`) | The check never reports these, but the fixer accepts a drifted column on one and rewrites it. A lambda parameter is pinned by its target descriptor, so the output stops compiling. Same unverified drift precondition as the row above |
| Drifted column landing on a different declaration of the same collection type | The fixer confirms a drifted column names a signature type, not that it is the type the violation described, so another concrete-collection declaration is rewritten unchecked. A warning-tier one still compiles, but two refused shapes do not: a return type withheld because it overrides a classpath method (rewriting it breaks covariance) and a parameter withheld because it would collapse onto an overload (two overloads with one erasure). Both leave a broken build after the file is written. This includes a declaration the check deliberately downgraded to the warning tier, since the error event supplied the column |
| Unparseable buffer containing no `record` token | With no parse, a drifted column is rewritten with no check that it names a signature type. Structural rather than an oversight, since there is nothing to check against. The "a sibling fixer must have damaged the buffer first" bound on this row and on the `record` row above is unverified: a leading BOM (`U+FEFF`) is known to make the fixer's parse fail, so if Checkstyle tolerates the BOM, every BOM'd file takes this path on a pristine buffer, which removes the sibling-edit precondition from this row and from the two drift rows above |
| Column drifted onto a nested type argument of a RECORD component (`record R(Map<String, ArrayList<String>> m)`) | A drifted column on the nested name is not treated as part of the record pair, so the component is rewritten alone. The result is an invariant substitution, and when the record writes its accessor out also a half-rewritten pair, which fails to compile with the JLS 8.10.3 error the record path exists to prevent |
