# PreferCollectionInterfaceCheck auto-fix coverage

Replaces a concrete collection type in a method or constructor signature with its interface
(e.g. `ArrayList` to `List`).

Every concrete collection type in a signature is reported. It is reported as an **error**, and so
auto-fixed, only when the rewrite is provably contained in this compilation unit; otherwise as a
**warning**, which the fix pipeline never applies. A rewrite that would be outright wrong is not
reported at all.

The two tiers ask different questions, because a parameter and a return type break differently:

| Position | What breaks | Auto-fixed when |
| --- | --- | --- |
| Parameter | An override in a file this run cannot see. Without `@Override` the two silently stop being a pair and dispatch changes | Nothing outside this file can override the member: it is a constructor, or `private`, or its declaring type is an enum, record or `final` class, or a type nothing can name to extend (an enum constant body, an anonymous class, a local class). An annotation type is listed in the same guard but is unreachable there, since its members parse as annotation fields rather than methods. `static` and `final` are NOT enough on their own: a subclass in a file this run cannot see still declares a same-named member, and the widened signature turns its legal overload into an illegal override of a `final` method, or makes a `static` one hide rather than overload |
| Return type | A caller in a file this run cannot see. Widening keeps every unseen override legal, so overridability is the wrong question here | Nothing outside this file can name the member to call it (`private`, or a declaring type that is an enum constant body, an anonymous class, or a local class) AND every call in this file still compiles and still binds. Each call's consuming position is decided by the same whitelist the parameter row uses, so a result assigned to a concrete-typed target, passed where the interface is rejected, or read through a method the interface does not declare holds the return type back. A result that survives only because ANOTHER return type widens is refused rather than chased, and a call reached through a method reference is refused, since neither names what consumes it |
| Record component | Both at once: the component types the canonical constructor's parameter and the accessor's return, and JLS 8.10.3 forces the two to stay identical. It therefore takes the return-type rule, applied to the record itself rather than to a member | Nothing outside this file can name the RECORD (`private`, or declared inside an enum constant body, an anonymous class, or a method body) AND every accessor call in this file accepts the interface, by the same rule as a return type. A top-level record is the most reachable shape there is, so its components are reported and never auto-fixed. One answer decides the component and its explicit accessor together, since the two must stay identical |

`static` and `final` stop a member being overridden but do nothing to stop it being called, which is
why they decide neither tier on their own.

A parameter is additionally held back from the error tier when an overload of the same name and
arity is reachable, since widening makes the signature applicable to calls that used to bind to
that overload and resolution then picks whichever is more specific, and when its own body only
survives widening because the return type moves to the same interface in the same pass, which
the two tiers may now decide differently.

The owner's visibility decides nothing in either tier: a public subtype in this package re-exports
the member, and any other package may then extend that subtype, so a package-private or `private`
nested owner is no protection.

A record component and its explicit accessor are rewritten in ONE edit, anchored on the component:
the accessor's own violation defers rather than fixing, so no arrival order of the two violations
can half-apply the pair, and if either half cannot be rewritten neither is. JLS 8.10.3 forces the
accessor's return type to be identical to its component's, so a half-rewrite does not compile
(`return type of accessor method items() must match the type of record component items`). Every
refusal below that names the pair is that rule: it costs the component's fix as well as the
accessor's.

## Not flagged by check (correct behavior, not a limitation)

| Pattern | Reason |
| --- | --- |
| Parameter list whose rewrite would duplicate another overload (`dump(List<String>)` alongside `dump(ArrayList<String>)`) | Only the parameter list is exempted; a return type cannot create an overload collision, so it is still flagged on both declarations (the sole exception is an override of a supertype outside this file, see below). Replacing the concrete type would make the two signatures identical and the file would stop compiling. Overloads are compared on their erased parameter types, positionally, which is the identity the compiler uses. A varargs parameter erases to an array, so `dump(ArrayList<String>...)` beside `dump(List<String>)` is still flagged; a type variable erases to its bound, and a same-file type is identified by where it is declared, so `Box` and `Outer.Box` are one type rather than two |
| Method whose rewrite would duplicate an overload declared on a same-file supertype or subtype | The two signatures would become an override or a hide instead of an overload, silently rebinding existing calls to the other method, or fail to compile outright when the access differs. Only the type itself and its subtypes can see the member, so those and their supertype chains are searched; sibling types are excluded, since neither inherits the other's members. A private member is skipped only in a supertype, where it is not inherited: a subtype declaring one whose erasure matches an inherited method is a weaker-access compile error, not an overload. Anonymous class bodies, enum constant bodies and local classes are linked to their supertypes too. Constructors are never inherited, so only the declaring body is searched. A static interface method is not counted, since an implementor does not inherit it. Two members whose erased parameter types are ALREADY identical are an override or hide pair rather than a collision the rewrite would create, so both are still flagged and both are rewritten, which preserves the relation |
| Method whose rewrite would duplicate an overload inherited from a supertype in another file | The supertype is resolved from the classpath and its methods compared on their erased parameter types, so the collision is caught even with no AST for it |
| Method that overrides one declared by a supertype outside this file (e.g. an override of a JDK method) | The supertype pins the signature: the parameters cannot change without breaking the override, the return type cannot widen without breaking covariance, and the supertype is not visible to be rewritten alongside it. This is the one case where the return type is exempted as well as the parameter list. The question is asked with the method's CURRENT erasure, so a method that would merely COLLIDE with an inherited overload once rewritten, rather than already overriding one, keeps its return-type violation |
| Record component whose rewrite would give the canonical constructor an explicit constructor's erasure | The component list is both the canonical constructor's parameters and the accessors' return types, so rewriting it would produce two constructors with one erasure |
| Type nested inside another type's type arguments (`Map<String, ArrayList<Integer>>`) | Generics are invariant, so this is a substitution rather than a widening: `Map<String, List<Integer>>` is not a supertype of `Map<String, ArrayList<Integer>>` and every call site breaks, including ones in this same file that the fix does not touch. The one position that genuinely widens is a `? extends` bound on a parameter, which is still flagged, and only when every enclosing type-argument level was itself entered through such a bound: an invariant level anywhere above it (`List<Set<? extends ArrayList<X>>>`) makes the rewrite a substitution again. The same bound on a return type narrows what the caller may assign, a record component is both at once, and a `? super` bound narrows everywhere, since raising its lower bound accepts fewer arguments |
| Parameter the body uses somewhere that demands the concrete type (`values.ensureCapacity(10)`, `items = values`, `values::trimToSize`) | Widening the parameter changes what every use of it may do, so each use is decided against its own target: a call or method reference the interface does not declare, an assignment into a concrete-typed variable, an argument the callee's parameter would reject, or a return the enclosing return type would reject. Positions that read the value through `Object` alone (concatenation, equality, `instanceof`, an enhanced `for`) always survive, as does writing through the name itself, since the target there is the declaration being widened. A target this file declares, or a callee the classpath cannot resolve, refuses rather than guesses. The refusal is per parameter, so a second parameter on the same method is still flagged. An array or varargs parameter widens its ELEMENT type, so `length` and indexing survive and it is the uses on an element that must hold. A record component is checked against every body in the record, since it is the canonical constructor's parameter and the accessor's return type at once |
| Simple name that this file declares as a type, even when an import gives the same spelling a collection (`Stack`, `Properties`) | Java resolves a type declared in this compilation unit ahead of an import, so resolving against the classpath would read the user's own type as a collection and rebind the signature to an unrelated one. Local classes and inherited member types count as declared |
| Signature whose replacement name is already bound in this file (`class List` of its own, or `import java.awt.List`) | The fix writes the bare simple name and adds a `java.util` import, so a file that already binds that name would have every other use of it silently rebound to `java.util`, or would stop compiling outright on the duplicate |
| Annotation name or annotation member name appearing inside a signature type (`@Ann(ArrayList = "x")`) | Neither is a type in the signature, so resolving them would rewrite the annotation itself. A type-use annotation is a sibling of the type it annotates rather than its parent, so skipping the subtree cannot hide an annotated type argument |

## Missed by check (unintended)

Nothing is reported, so neither the warning tier nor the fixer ever sees these. Unlike the rows
above, the silence is not a decision.

| Pattern | Reason |
| --- | --- |
| Array-typed record component whose explicit accessor returns it bare (`record R(ArrayList<String>[] items) { public ArrayList<String>[] items() { return items; } }`) | An array component widens its ELEMENT type, so `isWidenedUse` takes its array branch, which accepts an `INDEX_OP` first child and `.length` and refuses every other shape before the `return` is ever weighed against the accessor's own type. The non-array pair reaches that weighing and couples the two halves instead. The refusal is the component's, and `checkRecordComponents` skips the component and its accessor together on it |

## Not supported

| Pattern | Reason |
| --- | --- |
| Column out of range (negative, or at/past end of line) | The violation column is outside the line's content |
| No identifier at the violation column | The column does not point at a Java identifier character |
| Reported position that no longer names a type | An edit earlier in this pass changed the line count under the violation, so the position describes text the check never saw. The buffer is reparsed and no identifier stands there any more, while the line-local scan would happily rewrite whatever does. Reported as `reported position no longer names a type` |
| Class not resolvable | The class can't be resolved (missing from the classpath, or an unresolvable name) |
| Class is not a standard collection | The resolved class is an interface, abstract, ambiguous, or not in the supported set |
| Buffer that does not parse and spells `record` outside comments and literals | With no parse nothing tells a record component or accessor apart from an ordinary parameter or return type, and taking the line-local path there would rewrite one half of a pair alone, which does not compile. Checkstyle reports a parse error and runs no check on a file that does not parse, so the buffer got that way from an earlier fix in this pass. The scan reads the masked buffer, so the word inside a comment or a string does not refuse; it matches whole words, so an identifier spelled `record` does. A buffer that spells it nowhere has no pair to break and still takes the line-local path. Reported as `record component and accessor cannot be rewritten as one edit` |
| Position on a qualifier segment of a record component's or accessor's type (the `util` of `java.util.ArrayList`) | `isRecordPairPosition` calls any name under the component's or accessor's `TYPE` a pair position, while `recordTypePairAt` builds a pair only when that name is the type's OWN name (`typeNameNode`, the last segment of the chain), so a segment left of it is recognised without producing a pair, and the line-local path would rewrite the segment alone. The check logs at the chain's last `IDENT` and never at a segment, so this is reachable only from a position an earlier edit in this pass invalidated, or from a synthetic one. Reported as `record component and accessor cannot be rewritten as one edit` |
| Component or accessor name interrupted by a comment (`java./*note*/util.ArrayList`) | The rewrite replaces everything between the name's two ends with the interface name, so anything in there that is not the name would be deleted. Whitespace is what makes a qualified name broken across lines one span, so only whitespace is tolerated; a comment, or any other non-whitespace, refuses. The same guard refuses a span whose columns fall outside the lines it covers. Reported as `record component and accessor cannot be rewritten as one edit` |
| Component and accessor spellings that do not resolve to the same interface | Each half is resolved on its own, from its spelling through this file's package and imports, because the two need not be spelled alike (`ArrayList` against `java.util.ArrayList`). One replacement name is written into both halves, so a half that resolves to no concrete collection, or two halves that resolve to different interfaces, leave no name that fits both. Reported as `record component and accessor cannot be rewritten as one edit` |
| Violation reported on the accessor half of a record pair | Not a failure: the pair is one edit anchored on the component, so the accessor's violation defers and the component's carries the rewrite. Both halves are still checked for an intact span and a resolvable interface first, so an accessor violation reports the refusal reason when there is one rather than the deferral. Reported as `record accessor is rewritten with its component` |

## Known unsound

Unlike the rows above, these are not skips: the check flags and the fixer rewrites, and the result may not compile.

| Pattern | Reason |
| --- | --- |
| Method whose rewrite would duplicate an overload inherited from a supertype that is neither in this file nor loadable | The collision is decided against the supertype's declared methods, which needs either an AST here or a class the checkstyle run can load. With neither there is nothing to compare against, so the rewrite is applied blind. This is the DEFAULT for a supertype declared in a sibling source file, not an edge case: `CheckstylePlugin` puts only `compileClasspath` on the checkstyle configuration, never `sourceSets.main.output`, so a same-package sibling never loads. Adding the output directory would not fix it, because the guard would then be sound or unsound depending on whether a previous build left stale classes on disk. Since the severity split the exposure is confined to the error tier |
| Override pair where only one half is refused | Two members whose erased parameter types already match are treated as an override pair the rewrite preserves, on the premise that both halves are rewritten together. A refusal that applies to only one of them (its body needs the concrete type, it has no body to inspect, or only one half has a call site that holds it back) breaks that premise: the other half is rewritten alone, so the override silently becomes an overload, or an abstract method is left unimplemented |
| `? extends` bound on a parameter whose body uses the element's concrete API (`items.get(0).ensureCapacity(10)`) | The use-site check asks what the body calls on the parameter itself, which is the position the rewrite changes. Widening the bound also changes what the elements are known to be, and tracking that needs the type of an arbitrary expression rather than one declared name |
| Record component whose accessor a supertype already declares | The accessor's return type has to stay identical to its component (JLS 8.10.3), so a supertype that pins the accessor pins the component with it. A same-file supertype is left to the ordinary walk, which flags and rewrites both halves together, unless that declaration is itself refused (nothing outside this file can call it, or it overrides a method from the classpath); the transitive closure is searched, since the accessor may sit on an interface the record only reaches through another. A supertype this run cannot resolve, cannot load, or whose members cannot be read is refused outright, since nothing here can show it does not declare the accessor and no violation would ever be reported against it |
| Signature naming a nested classpath type (`Map.Entry`) whose override or collision guard should have caught it | The rewritten spelling is normalized through the loaded class's binary name (`java.util.Map$Entry`) while the erasure comparison reads canonical names (`java.util.Map.Entry`), so the two never match and the guard reports no override. Verified: `declaresMethodErasure` returns false for the binary form |
| Receiver call where the concrete type declares a narrower overload the interface lacks (`contains(String)` beside `Collection.contains(Object)`) | Overloads are paired by positional assignability so a bounded type variable still matches, which cannot be told apart from a genuinely more specific overload. The call silently rebinds to the interface's general form. The pairing also stops at the first match, so which overload supplies the return-type comparison depends on unspecified `getMethods()` order |
| Method whose classpath supertype loads but whose members cannot be read | `declaresMethodErasure` reads the supertype through helpers that fold a `LinkageError` into an empty array, so an unreadable supertype answers "declares no such method" and the signature it pins is rewritten. The probe that distinguishes the two is wired only into the record-accessor path. Since the severity split the exposure is confined to the error tier |
| Array return type or array record component | The tier is decided against the ELEMENT type. `ARRAY_DECLARATOR` is a sibling of the type name under `TYPE` rather than a wrapper around it, so `TYPE.getFirstChild()` is the name either way, an array declaration is judged exactly as the non-array one, and it is auto-fixed on the same conditions. Every consuming position is therefore weighed for `ArrayList` when the value is an `ArrayList[]`, and those are not the same question: a target, an argument or a return is asked whether it accepts `java.util.List` while what reaches it is a `List<String>[]`. For the cases we know of the direction is conservative, costing coverage rather than correctness: an `Object[]` or varargs parameter takes the array but not the element type, so the argument check finds no candidate and refuses |
| Type that no other file can subclass but that the tier still treats as extendable (a `sealed` type, or a class whose constructors are all `private`) | Costs coverage, never correctness: the member is reported as a warning rather than auto-fixed. Recovering it needs the same-file subtype closure, because both shapes are defeated by a same-file public subtype that re-exports the member, so neither can be decided from the declaration alone |
| Column drifted onto a nested type argument (`Map<String, ArrayList<String>>`) | The fixer's staleness gate accepts any identifier that climbs to a signature `TYPE`, and that climb passes through `TYPE_ARGUMENTS`/`TYPE_ARGUMENT`/`TYPE_LOWER_BOUNDS`. The check refuses those same positions via `substitutesATypeArgument`, so the gate is wider than the log set it is meant to re-validate: a column an earlier fixer in the same pass shifted can land on the nested name and rewrite it, producing the invariant substitution `Map<String, List<String>>` that the "Not flagged" table exists to prevent. `? super ArrayList` has the same shape. The drift precondition is UNVERIFIED: seven fixers emit a `FixResult` whose `startLine` is above their own event line, which is the shift mechanism, but no fixture has been shown to land a shifted column back inside a signature type. If one can, this is severe rather than moderate |
| Column drifted onto a lambda or catch parameter (`(ArrayList list) -> ...`) | `PARAMETER_DEF` is also a lambda's explicit parameter and a `LITERAL_CATCH` parameter, neither of which the check visits: `checkParameters` is reached only from `visitScopedToken`'s `METHOD_DEF`/`CTOR_DEF` arms. The gate tests the token type without testing that the owner is a real signature, so a drifted column rewrites the lambda parameter, which is pinned by its target descriptor and stops compiling. Same unverified drift precondition as the row above. Closing it means requiring the `PARAMETER_DEF`'s parent to be a `PARAMETERS` under a `METHOD_DEF` or `CTOR_DEF` |
| Drifted column landing on a different declaration of the same collection type | The gate is shape-based: it proves the position IS a signature type, never that it is THE type the violation described. A re-anchored column on another concrete-collection declaration is rewritten with no downstream check. Where the other declaration is merely warning-tier the output still compiles, but the gate also bypasses two refusal classes whose output does NOT: a return type withheld by `overridesAClasspathMethod` (rewriting it breaks covariance) and a parameter withheld by `collapsesOntoAnOverload` (rewriting it produces two overloads with one erasure). Both leave a broken build after the pipeline has written the file and begun its second pass. This includes a declaration the check deliberately downgraded to the warning tier, whose auto-fix the pipeline's `SeverityLevel.ERROR` filter would otherwise have withheld, because the error event supplied the column. Closing it needs the gate coupled to the violation message's replacement argument, since autofixability depends on `useSites`/`typeGraph` state the fixer does not hold |
| Unparseable buffer containing no `record` token | When `FixerAst.parseOrNull` returns null and no masked line carries the word `record`, control reaches the line-local scan with no AST gate at all: only the `identStart` check and the reflective resolve stand between a drifted column and a rewrite. Structural rather than an oversight, since there is no AST to gate against, but it is the one route around the staleness gate. The "a sibling fixer must have damaged the buffer first" bound on this row and on the `record`-token row above is UNVERIFIED: it assumes the fixer's parser and Checkstyle's see the same bytes, and they do not. Checkstyle reads through `FileText(File, charset)` while the fixer parses a reconstruction from `Files.readString`, which preserves a leading `U+FEFF`, and a leading BOM is known to make `FixerAst.parseOrNull` fail. If Checkstyle's read path tolerates the BOM, every BOM'd file takes this ungated path on a PRISTINE buffer, which removes the sibling-edit precondition from this row and from the two drift rows below. Settle it by running the pipeline over a file starting with the bytes `EF BB BF` and checking whether the check still reports while `parseOrNull` returns null |
| Column drifted onto a nested type argument of a RECORD component (`record R(Map<String, ArrayList<String>> m)`) | The two positional gates climb different node sets. `isRecordPairPosition` ascends only `DOT` and `ARRAY_DECLARATOR`, while `namesATypeIdentifierAt` ascends the full `isTypeStructure` set. For a column on the nested name, `recordTypePairAt` returns null (the nested name is not the type's own name), `isRecordPairPosition` ALSO returns false (its climb stops at `TYPE_ARGUMENT`), but `namesATypeIdentifierAt` returns true, so control reaches the line-local scan and rewrites the component alone. This is the one route where a genuine record position escapes the `RECORD_PAIR_HALF` guard; every other null return from `recordTypePairAt` is caught by `isRecordPairPosition`. The result is both an invariant substitution AND a half-rewritten pair, which fails to compile with the JLS 8.10.3 error the record path exists to prevent. Fix is to make the climb loop call `isTypeStructure` so the pair guard can never recognise fewer positions than the gate whose failure falls through to a line-local rewrite |
