# ControlFlowBracesCheck auto-fix coverage

## Non-do-while sub-rules

The fixer adds braces to braceless multi-line bodies, removes unnecessary braces from single-line
bodies, moves one-liner bodies to their own line, and handles brace-on-own-line formatting.
Do-while violations are handled separately (see the do-while sub-rules below).

| Violation type | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| Missing braces (if) | `if (cond)\n\tfor (...)\n\t\tstmt;` | Yes | Wraps in `{ }`, preserves body indentation |
| Missing braces (else) | `else\n\tfor (...)\n\t\tstmt;` | Yes | Same wrapping logic |
| Missing braces (for) | `for (...)\n\tif (...)\n\t\tstmt;` | Yes | Same wrapping logic |
| Missing braces (for-each) | `for (var x : list)\n\tif...\n\t...` | Yes | Same wrapping logic |
| Missing braces (while) | `while (cond)\n\tif (...)\n\t...` | Yes | Same wrapping logic |
| Missing braces + trailing comment | `if (cond) // note\n\tfor...\n\t\tstmt;` | Yes | Inserts `{` before the `//` comment |
| Missing braces (braced inner control body) | `for (...)\n\tif (...) { ... }\n\tstmt;` | Yes | The body ends at the inner block's `}`, so a trailing sibling statement stays outside the new braces. Covers if/else/for/while/try/switch/synchronized inner bodies and their else/catch/finally continuations. An `else` after that `}` continues the body when an `if` at the body's own nesting level claims it (`if (c)\n\tif (d) { ... }\n\telse ...`), and stays outside the new braces when it binds to the statement enclosing the body (`if (c)\n\tfor (...) { ... }\nelse ...`). An `if` written inside a deeper block is already closed by that block's own `}` and cannot claim the `else` |
| Missing braces (labeled inner body) | `while (c)\n\tloop: for (...) { ... }\n\tstmt;` | Yes | A labeled block still ends at its own `}` and a trailing sibling statement stays outside the new braces. Covers stacked labels (`outer: inner:`), a label alone on its line, and labels containing supplementary characters |
| Missing braces (expression-brace body) | `if (cond)\n\tx = new int[]{...};` | Yes | Expression-brace (`{...}`) closed by a `;` is not treated as the control body's block end; the whole assignment statement is wrapped. Covers array initializers, anonymous classes, and lambda bodies |
| Missing braces (braceless if-else body) | `for (...)\n\tif (c)\n\t\tx;\n\telse\n\t\ty;` | Yes | The whole `if`-`else` is wrapped, including else / else-if chains / braced else / else-branch loops. An `else` that binds to an enclosing `if` (e.g. a `for`/`while` body followed by an outer `else`, or an `if` written inside a braceless `do` whose `while (...);` has already closed it) is left outside the new braces |
| Missing braces (do-while body) | `if (c)\n\tdo\n\t\tstmt;\n\twhile (x);` | Yes | A braceless `do`'s body `;` does not end the enclosing statement: it runs on through the do-while's own `while (...);`, so the whole loop is wrapped. An `else` after that terminator still binds to the enclosing `if` and is wrapped with it |
| Body cannot be located from the parse | a buffer that does not parse, or one where an earlier fix in the same pass moved the reported node | No | Only reachable after an earlier fix in the same pass. Reported as `cannot reshape the body: it cannot be located without a parse` when the buffer did not parse, and `cannot reshape the body: an earlier fix in this pass moved it` when it did. The do-while route reports `cannot reshape the do-while body: its required form cannot be determined without a parse` and the stale-position message respectively |
| Unnecessary braces (if) | `if (cond) {\n\tsingleStmt;\n}` | Yes | Removes `{` and `}`, preserves `else` on own line. Not when the statement ends in a dangling `if`; see the else-rebind row below |
| Unnecessary braces (else) | `else {\n\tsingleStmt;\n}` | Yes | Same removal logic |
| Unnecessary braces (while) | `while (cond) {\n\tsingleStmt;\n}` | Yes | Same removal logic |
| Unnecessary braces (for) | `for (...) {\n\tsingleStmt;\n}` | Yes | Same removal logic. `PreferBulkOperation` can also fire on the same loop; the pipeline still converges on the bulk call |
| Brace on own line (if) | `if (cond)\n{\n\tstmt;\n}` | Yes | Removes `{` and `}` lines |
| Brace on own line (else) | `else\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Brace on own line (while) | `while (cond)\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Brace on own line (for) | `for (...)\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Body shares the `{` line | `if (cond) { stmt;\n}` | No | The statement sits on the line the fixer rebuilds, so re-emitting the keyword line without the brace would drop it; reported as `cannot remove the braces: other content shares the brace line` |
| Unnecessary braces + line comment on `{` | `if (cond) { // note\n\tstmt;\n}` | Yes | The comment documents the statement, not the block, so it stays on the keyword line: `if (cond) // note` |
| Unnecessary braces + block comment on `{` | `if (cond) { /* note */\n\tstmt;\n}` | No | A block comment can be followed by code on the same line, so it is not carried over blindly; reported as `cannot remove the braces: other content shares the brace line` |
| Brace on own line + comment on the `{` line | `if (cond)\n{ // note\n\tstmt;\n}`, `if (cond)\n/* note */ {\n\tstmt;\n}` | No | The brace line is dropped whole, so anything sharing it, before or after the `{`, would go with it; reported as `cannot remove the braces: other content shares the brace line` |
| Block does not end on the line after the body | `if (cond) {\n\ts = """\n} """; }` | No | A `}` that exists only inside a text block or comment is never taken for the block's end. When the first real token on the line after the body is something else (here a text block's closing delimiter and the statement's `;`), the block does not end where the fixer would splice; reported as `cannot reshape the body: the block does not end where the body does` |
| Comment ahead of the closing `}` | `if (cond) {\n\tstmt;\n\t/* note */ }`, `if (cond) {\n\tstmt; /* note\n\t} */ }` | No | The comment occupies the line the fixer would drop. Covers a comment that opens and closes on the brace line and one carried down from an earlier line, whose own `}` is never mistaken for the block's end; reported as `cannot remove the braces: other content shares the brace line` |
| Variable or local-type declaration body | `if (cond) {\n\tint x = 5;\n}`, `for (...) {\n\tclass Local {}\n}` | n/a | Not reported: a declaration is a block statement rather than a statement (JLS 14.2), so it can only appear inside a block and its braces are load-bearing. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `cannot remove the braces: the body is a declaration, so they are load-bearing`. A leading `/* note */`, tab-separated tokens, and an apostrophe inside an annotation's comment argument do not hide the declaration. A labelled jump (`break outer;`, `continue outer;`) is unbraced rather than read as a `Type name;` declaration |
| Block whose statement ends in a dangling `if`, with an `else` outside it | `if (a) {\n\tif (c && d());\n}\nelse\n\ty();`, `if (a)\n\twhile (c) {\n\t\tif (c && d());\n\t}\nelse\n\ty();` | No | Java binds an `else` to the nearest preceding `if` that lacks one, so dropping the braces hands the following `else` to the `if` inside the block. The re-bound code still compiles, which is why it has to be refused rather than caught downstream. Both brace-removal paths refuse when the block's statement ends in an `if` with no `else` of its own (following the trailing-substatement chain: an `if` to its `else`, an `else`/`while`/`for`/label to its body) and the walk out of the block reaches an `if` that owns an `else`, passing through the same constructs plus `do`. Reported as `cannot remove the braces: a following else would bind to an if inside them` |
| One-liner (if / else / for / for-each / while) | `if (cond) stmt;` | Yes | The body moves to its own line one level deeper. A `;` in the `for` header, a `{` in an array-initializer or lambda, and `;` inside strings or comments never move the split point |
| One-liner whose body spans lines | `if (cond) run(() -> {\n\t...\n});` | Yes | Braces are added and the body's continuation lines are re-indented with it, since a multi-line braceless body is what the check would flag next. Also covers a nested one-liner (`if (c) if (d) stmt;`), whose inner statement lands on its own line first, and a body whose first token leads a continuation line (`if (c) list\n\t\t.add(1);`) |
| One-liner with `else` on the same line | `if (c) a(); else b();` | Yes | The `else` continuation is emitted on its own line at the keyword's indent, so the pair resolves without a second pass. Covers `else if` chains |
| One-liner followed by a second statement | `if (c) a(); b();` | Yes | Only the body moves; the sibling statement is re-emitted at the keyword's indent |
| One-liner with a trailing comment | `if (c) a(); // note` | Yes | A comment after the body annotates it, so it travels with the body instead of being left on the keyword line |
| One-liner body terminated on a later line | `if (c) call()\n\t\t;` | Yes | The body's `;` is folded into the span, so the added braces enclose the whole statement |
| One-liner whose last line carries a following statement | `if (c) call(\n\t\tx); other();` | Yes | The body's `;` bounds the block, so the sibling statement is re-emitted after the closing brace instead of being swallowed by it. When the body is itself a control statement it has no `;`, and the bound comes from the construct that resumes on that line: the statement's own `else`, or the next statement in the enclosing block (for an `else` body, the enclosing `if`'s sibling) |
| Cuddled `else` one-liner | `} else stmt;` | Yes | A keyword sharing its line with a closing brace is handled like any other; the brace stays cuddled |
| No control-flow keyword at the violation site | a stale coordinate on a line that carries no keyword at all | No | Reported as `cannot reshape the body: no control flow keyword at the violation site`. The keyword is matched as a whole token anywhere on the line outside comments and literals, so a cuddled `} else stmt;` has one and `elseIf`, `forEach`, or `whileLoop` do not. A keyword separated from its condition by a TAB (`if\t(c) stmt;`) is recognised too |
| Body's last line opens an unterminated literal | `if (c)\n\tif (d)\n\t\t--x; /* multi\n\t\t   line */` | No | The added `}` is emitted after the body's last line, which would put it inside a block comment or text block still open there; reported as `cannot reshape the body: a block comment or text block does not close on the line it opens` |
| Header spans lines | `if (a\n\t\t&& b) { ... }` | No | Every handler rewrites the keyword line and takes the body from the lines after it, so a header that has not closed by then would be spliced mid-condition; reported as `cannot reshape the body: the control flow header spans multiple lines` |
| Text block in body | `if (cond) s = """...""";` | Yes | The body's continuation lines shift by one level, the closing delimiter with them, so the block's incidental indentation (and therefore its value) is unchanged. A blank line inside the block is left blank rather than indented: blank lines do not participate in incidental indentation, and indenting one would leave whitespace-only content behind. The do-while path refuses text blocks instead; see that table |

## Do-while sub-rules

The do-while fixer reshapes the body to its formatting tier. An assignment whose RHS is a chained
call or a `new` expression is tier 3, consistent with a bare chained call or `new` body; a single
non-chained call RHS stays tier 2. Comment, string, and char content in the body does not affect
the tier.

| Violation type | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| Tier-2 collapse | `do {\n\t--x;\n} while(...)` | Yes | Simple body (inc/dec, simple assign/compound, single non-chained call) collapses to do line |
| Tier-2 collapse with comment/literal | `do {\n\ts = "// not";\n} while(...)` | Yes | Comment/string/char content in the body does not change the tier |
| `while` text inside the body or on the `}` line | `do x = x + y; // ; while` / `do {\n\t--x;\n} // meanwhile` | Yes | A `while` inside a literal, inside a comment, inside an identifier (`whileCount`), or nested in a braced body or lambda on the same line is never mistaken for the one that closes the statement |
| `while` claimed by a nested do-while | `do do { --x; ++x; } while (x > 5); while (x > 0);` | Yes | A nested `do` on the same line claims the next `while` at that nesting level, so the split lands on the outer statement's own terminator rather than the inner one's. An identifier that merely contains `do` (`undo`, `doWork`) never claims a `while` |
| Statement after the closing `while` | `do --x; while (x > 0); while (y > 0) { --y; }` | Yes | A sibling `while` loop written after it stays on the re-emitted `while` line instead of being taken for the condition |
| Tier-3 expand | `do x = x + y; while(...)` | Yes | Complex RHS (binary op), chained call, or `new` body moves to its own line |
| Tier-3 assign chained/new RHS | `do x = a.b().c(); while(...)` | Yes | Chained-call or `new`-expression RHS is tier 3 (matches the bare-call / bare-`new` body) |
| Tier-3 with the `while` cuddled onto the body line | `do\n\tx = x + y; while (x < 100);` | Yes | The body is already on its own line, so only the terminator moves: reported as `Do-while 'while' clause must be on its own line.`, the same message the tier-2 shape uses. Covers a binary-operator RHS and a chained-call RHS |
| Tier-3 braced body | `do if (c) { x(); } while (y);` | Yes | Covers `if`, `while`, `for`, `switch`, `synchronized`, and try-with-resources bodies, a trailing block comment after the `}`, and the `while` sitting on the next line. A one-line `try`/`catch` or `try`/`finally` is handled the same way |
| Body shares the `{` line | `do { --x;\n} while (x > 0);` | No | The statement sits on the line the fixer rebuilds, so re-emitting the `do` line without the brace would drop it; reported as `cannot remove the braces: other content shares the brace line` |
| Comment ahead of the own-line `{` | `do\n\t/* note */ {\n\t--x;\n}\nwhile (...)` | No | The comment occupies the line the fixer rebuilds; reported as `cannot remove the braces: other content shares the brace line` |
| Comment on the `do {` line, the `}` line, or between | `do { // guard` / `} // note` / a comment line before the `while` | Yes | The braces go away but their comments do not: a comment on the `do {` line rides along on the rebuilt `do` line, and one on the `}` line or between it and the `while` is re-emitted ahead of the `while`. Code in those positions has no home and is refused instead |
| Comment on the `do` line plus a second comment on the `{` line or the body | `do // note\n{ // brace note\n\t--x;\n}\nwhile (c);`, `do // note\n{\n\t--x; // pending\n}\nwhile (c);` | No | Only one comment can ride the rebuilt `do` line: a second `//` trailer behind the first would be swallowed by it, and in tier 2 the body joins that same line ahead of its own trailing comment. Reported as `cannot remove the braces: other content shares the brace line` |
| Unterminated block comment or text block on the line it opened | `do /* multi\n\tline */\n\tx = 5;\nwhile (...)`, `do { /* multi\n\tline */ --x;\n} while (...)`, `} /* multi\n\tline */\n\twhile (...)` | No | The literal does not close on that line, so the text below it is literal content rather than code: rebuilding the line would carry the opener away from what it covers, and a brace appended to it would land inside the literal. Applies to the `do` line, the `do {` line, the `}` line, and a non-do-while keyword line; reported as `cannot reshape the body: a block comment or text block does not close on the line it opens` |
| Comment ahead of the closing `}` | `do {\n\t--x;\n\t/* note */ } while (x > 0);` | No | The comment occupies the line the fixer would drop; reported as `cannot remove the braces: other content shares the brace line` |
| Multi-line braced body | `do {\n\t--x;\n\t--y;\n} while(...)` | n/a | Not reported: a body of more than one statement needs its braces, so there is nothing to collapse. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `cannot remove the braces: the do-while body spans multiple lines` |
| Another do-while ahead of it on the line | `do do --x; while (x > 5); while (x > 0);` (the inner statement), `do; while (c); do --y; while (y > 0);` | No | The statement is rebuilt from the reported keyword's own indentation, so a do-while written ahead of it on the same line would be dropped. The outer statement is reshaped first, which puts the inner one on a line of its own, and the next pass fixes it; reported as `cannot reshape the do-while: it shares its line with another do-while` |
| Buffer does not parse / no do-while at violation | bare fragment / mid-fix damaged source / stale violation column | No | Neither the tier nor the terminator's position can be determined when the buffer fails to parse or when it parses but no `do` keyword sits at the reported position. Reported as `cannot reshape the do-while body: its required form cannot be determined without a parse` when the buffer did not parse, and `cannot reshape the body: an earlier fix in this pass moved it` when it did |
| Empty braced body | `do {\n} while (c);` | n/a | Not reported: an empty block has no statement to reshape. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `cannot reshape the body: it is empty` |
| Comment-only braced body | `do {\n\t// note\n} while (c);` | n/a | Not reported: a block holding only comments has no statement to collapse. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `cannot reshape the do-while body: it has no statement` |
| Text block in body | `do s = """..."""; while(...)` | No | Skipped (`cannot reshape the do-while body: it contains a text block`): the body's text block spans lines that the reshaped one-line (tier 2) or two-line (tier 3) body cannot carry, so reshaping it would change the block's incidental indentation and therefore its value |
| `while` on a comment/text-block close line | `do\n\tx = 1; /* c\n\t*/ while (...)` | No | Skipped: "cannot reshape the body: a block comment or text block does not close on the line it opens". Every reshape re-emits the terminator's line at the keyword's indent, so a line that begins inside a block comment or text block would carry that literal's content away from its opener |
| Body running onto the terminator's line | `do list\n\t\t.add(1); while (c);` | No | Skipped: "cannot reshape the do-while body: it runs onto the line its closing while shares". The body opened on the `do` line and continues onto the line the `while` shares, and neither tier form has a second body line to put that text on |
| Body continuing past the `do` line | `do x = x\n\t\t+ 1;\nwhile (c);`, `do x = foo()\n\t\t.bar();\nwhile (c);` | No | Skipped: "cannot reshape the do-while body: it does not end in a semicolon". Only the text on the `do` line is available to the reshaped body, and it stops mid-expression, so emitting it as the whole body would drop the continuation. A `;` inside a trailing comment or string does not count as the terminator |
| Comment ahead of the terminator | `do\n\t--x;\n/* note */ while (c);` | Yes | A comment sharing the terminator's line annotates the statement, so it rides on the re-emitted clause instead of being stranded |
| Terminating `while` cuddled onto the body's last line | `do\n\tif (c)\n\t\t--x;\n\telse\n\t\t--z; while (c);\nwhile (d)\n\t--z;` | Yes | That line splits: the body part stays where it is and the terminator moves down onto the added closing brace. A sibling `while` loop written below at the same indentation is not mistaken for the terminator, and neither is a terminator indented differently from its `do` |
