# ControlFlowBracesCheck auto-fix coverage

## Non-do-while sub-rules

The fixer adds braces to braceless multi-line bodies, removes unnecessary braces from single-line
bodies, moves one-liner bodies to their own line, and handles brace-on-own-line formatting.
Do-while violations are handled separately (see main table).

| Violation type | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| Missing braces (if) | `if (cond)\n\tfor (...)\n\t\tstmt;` | Yes | Wraps in `{ }`, preserves body indentation |
| Missing braces (else) | `else\n\tfor (...)\n\t\tstmt;` | Yes | Same wrapping logic |
| Missing braces (for) | `for (...)\n\tif (...)\n\t\tstmt;` | Yes | Same wrapping logic |
| Missing braces (for-each) | `for (var x : list)\n\tif...\n\t...` | Yes | Same wrapping logic |
| Missing braces (while) | `while (cond)\n\tif (...)\n\t...` | Yes | Same wrapping logic |
| Missing braces + trailing comment | `if (cond) // note\n\tfor...\n\t\tstmt;` | Yes | Inserts `{` before the `//` comment |
| Missing braces (braced inner control body) | `for (...)\n\tif (...) { ... }\n\tstmt;` | Yes | The body's extent comes from the check's AST, so it ends at the inner block's `}` and a trailing sibling statement stays outside the new braces. Covers if/else/for/while/try/switch/synchronized inner bodies and their else/catch/finally continuations. Which `if` an `else` after that `}` belongs to is the parser's answer: it continues the body when an `if` at the body's own nesting level claims it (`if (c)\n\tif (d) { ... }\n\telse ...`), and stays outside the new braces when it binds to the statement enclosing the body (`if (c)\n\tfor (...) { ... }\nelse ...`). An `if` written inside a deeper block is already closed by that block's own `}` and cannot claim the `else` |
| Missing braces (labeled inner body) | `while (c)\n\tloop: for (...) { ... }\n\tstmt;` | Yes | A label is part of the statement it names in the AST, so a labeled block still ends at its own `}` and a trailing sibling statement stays outside the new braces. Covers stacked labels (`outer: inner:`), a label alone on its line, and labels containing supplementary characters |
| Missing braces (expression-brace body) | `if (cond)\n\tx = new int[]{...};` | Yes | Expression-brace (`{...}`) closed by a `;` is not treated as the control body's block end; the whole assignment statement is wrapped. Covers array initializers, anonymous classes, and lambda bodies |
| Missing braces (braceless if-else body) | `for (...)\n\tif (c)\n\t\tx;\n\telse\n\t\ty;` | Yes | The whole `if`-`else` is wrapped: the parser puts the `else` inside the body statement, so else / else-if chains / braced else / else-branch loops are all included. An `else` that binds to an enclosing `if` (e.g. a `for`/`while` body followed by an outer `else`, or an `if` written inside a braceless `do` whose `while (...);` has already closed it) is left outside the new braces |
| Missing braces (do-while body) | `if (c)\n\tdo\n\t\tstmt;\n\twhile (x);` | Yes | A braceless `do`'s body `;` does not end the enclosing statement: it runs on through the do-while's own `while (...);`, so the whole loop is wrapped. An `else` after that terminator still binds to the enclosing `if` and is wrapped with it |
| Body cannot be located from the parse | a buffer that does not parse, or one where an earlier fix in the same pass moved the reported node | No | Every body span comes from the check's own AST classifier. A buffer that does not parse cannot have produced a violation in the first place, since checkstyle reports a parse error and runs no check; a parsed buffer with no node at the reported position means a sibling fix moved it. The fixer returns a `SkipResult` rather than re-deriving the body from raw text, and reports the two apart: `cannot locate the control-flow body without a parse` when the buffer did not parse, and `no control-flow body at the reported position; an earlier fix in this pass moved it` when it did. The do-while route splits the same way, reporting `cannot tell which do-while form the body needs without a parse` and the stale-position message respectively |
| Unnecessary braces (if) | `if (cond) {\n\tsingleStmt;\n}` | Yes | Removes `{` and `}`, preserves `else` on own line |
| Unnecessary braces (else) | `else {\n\tsingleStmt;\n}` | Yes | Same removal logic |
| Unnecessary braces (while) | `while (cond) {\n\tsingleStmt;\n}` | Yes | Same removal logic |
| Unnecessary braces (for) | `for (...) {\n\tsingleStmt;\n}` | Yes | Same removal logic. `PreferBulkOperation` can also fire on the same loop; the pipeline still converges on the bulk call (integration-tested for the braced and one-liner forms) |
| Brace on own line (if) | `if (cond)\n{\n\tstmt;\n}` | Yes | Removes `{` and `}` lines |
| Brace on own line (else) | `else\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Brace on own line (while) | `while (cond)\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Brace on own line (for) | `for (...)\n{\n\tstmt;\n}` | Yes | Same removal logic |
| Body shares the `{` line | `if (cond) { stmt;\n}` | No | The statement sits on the line the fixer rebuilds, so re-emitting the keyword line without the brace would drop it; reported as `cannot remove braces without losing other content on the brace line` |
| Unnecessary braces + line comment on `{` | `if (cond) { // note\n\tstmt;\n}` | Yes | The comment documents the statement, not the block, so it stays on the keyword line: `if (cond) // note` |
| Unnecessary braces + block comment on `{` | `if (cond) { /* note */\n\tstmt;\n}` | No | A block comment can be followed by code on the same line, so it is not carried over blindly; reported as `cannot remove braces without losing other content on the brace line` |
| Brace on own line + comment on the `{` line | `if (cond)\n{ // note\n\tstmt;\n}`, `if (cond)\n/* note */ {\n\tstmt;\n}` | No | The brace line is dropped whole, so anything sharing it, before or after the `{`, would go with it. The `{` is located on a comment/literal-masked copy, so a comment ahead of it is detected rather than read as the body; reported as `cannot remove braces without losing other content on the brace line` |
| Block does not end on the line after the body | `if (cond) {\n\ts = """\n} """; }` | No | The `}` is looked for on a comment/literal-masked copy of the buffer, so a `}` that exists only inside a text block or comment is never taken for the block's end. When the first real token on the line after the body is something else (here a text block's closing delimiter and the statement's `;`), the block does not end where the fixer would splice; reported as `the block does not end where the body does` |
| Comment ahead of the closing `}` | `if (cond) {\n\tstmt;\n\t/* note */ }`, `if (cond) {\n\tstmt; /* note\n\t} */ }` | No | The `}` is located on a comment/literal-masked copy of the buffer, so text the mask blanked still occupies the line the fixer would drop. Covers a comment that opens and closes on the brace line and one carried down from an earlier line, whose own `}` is masked and so never mistaken for the block's end; reported as `cannot remove braces without losing other content on the brace line` |
| Variable or local-type declaration body | `if (cond) {\n\tint x = 5;\n}`, `for (...) {\n\tclass Local {}\n}` | n/a | Not reported: a declaration is a block statement rather than a statement (JLS 14.2), so it can only appear inside a block and its braces are load-bearing. The fixer still refuses one independently on the three brace-removal paths, guarding against a stale column or a sibling fixer's rewrite, and reports `control-flow body is a declaration, so its braces are load-bearing`. It reads the body line through a comment/literal mask so a leading `/* note */`, tab-separated tokens, and an apostrophe inside an annotation's comment argument do not hide the declaration. Statement keywords are excluded by name, so a labelled jump (`break outer;`, `continue outer;`) is unbraced rather than read as a `Type name;` declaration |
| One-liner (if / else / for / for-each / while) | `if (cond) stmt;` | Yes | The body moves to its own line one level deeper. Its start comes from the check's AST, so a `;` in the `for` header, a `{` in an array-initializer or lambda, and `;` inside strings or comments never move the split point |
| One-liner whose body spans lines | `if (cond) run(() -> {\n\t...\n});` | Yes | Braces are added and the body's continuation lines are re-indented with it, since a multi-line braceless body is what the check would flag next. Also covers a nested one-liner (`if (c) if (d) stmt;`), whose inner statement lands on its own line first, and a body whose first token leads a continuation line (`if (c) list\n\t\t.add(1);`) |
| One-liner with `else` on the same line | `if (c) a(); else b();` | Yes | The `else` continuation is emitted on its own line at the keyword's indent, so the pair resolves without a second pass. Covers `else if` chains |
| One-liner followed by a second statement | `if (c) a(); b();` | Yes | Only the body moves; the sibling statement is re-emitted at the keyword's indent |
| One-liner with a trailing comment | `if (c) a(); // note` | Yes | A comment after the body annotates it, so it travels with the body instead of being left on the keyword line |
| One-liner body terminated on a later line | `if (c) call()\n\t\t;` | Yes | The body's `;` is folded into the span, so the added braces enclose the whole statement |
| One-liner whose last line carries a following statement | `if (c) call(\n\t\tx); other();` | Yes | The body's `;` bounds the block, so the sibling statement is re-emitted after the closing brace instead of being swallowed by it. When the body is itself a control statement it has no `;`, and the bound comes from the construct that resumes on that line: the statement's own `else`, or the next statement in the enclosing block (for an `else` body, the enclosing `if`'s sibling) |
| Cuddled `else` one-liner | `} else stmt;` | Yes | The body span comes from the check's AST at the reported column, not from a keyword prefix test anchored at the start of the line, so a keyword sharing its line with a closing brace is handled like any other. Nothing in the pipeline un-cuddles the brace, so refusing here left the one-liner unfixed |
| No control-flow keyword at the violation site | a stale coordinate on a line that carries no keyword at all | No | Nothing in the AST at the reported position and no recognisable keyword on the line; reported as `no control-flow keyword at the violation site`. The keyword is searched for across the whole line as a whole token, on a comment/literal-masked copy: anchoring it at the start would call a cuddled `} else stmt;` keyword-less even though the check reports at the `else`, and matching by substring would find one inside `elseIf`, `forEach`, or `whileLoop`. A keyword separated from its condition by a TAB (`if\t(c) stmt;`) is recognised too |
| Body's last line opens an unterminated literal | `if (c)\n\tif (d)\n\t\t--x; /* multi\n\t\t   line */` | No | The added `}` is emitted after the body's last line, which would put it inside a block comment or text block still open there; reported as `block comment or text block does not close on the line it opened` |
| Header spans lines | `if (a\n\t\t&& b) { ... }` | No | Every handler rewrites the keyword line and takes the body from the lines after it, so a header that has not closed by then would be spliced mid-condition; reported as `control-flow header spans lines` |
| Text block in body | `if (cond) s = """...""";` | Yes | The body's continuation lines shift by one level, the closing delimiter with them, so the block's incidental indentation (and therefore its value) is unchanged. A blank line inside the block is left blank rather than indented: blank lines do not participate in incidental indentation, and indenting one would leave whitespace-only content behind. The do-while path refuses text blocks instead; see that table |

## Do-while sub-rules

The do-while fixer reshapes the body to its formatting tier. An assignment whose RHS is a chained
call or a `new` expression is tier 3, consistent with a bare chained call or `new` body; a single
non-chained call RHS stays tier 2. Comment, string, and char content in the body does not affect
the tier.

| Violation type | Pattern | Auto-fix | Notes |
| --- | --- | --- | --- |
| Tier-2 collapse | `do {\n\t--x;\n} while(...)` | Yes | Simple body (inc/dec, simple assign/compound, single non-chained call) collapses to do line |
| Tier-2 collapse with comment/literal | `do {\n\ts = "// not";\n} while(...)` | Yes | Comment/string/char content in the body does not change the tier |
| `while` text inside the body or on the `}` line | `do x = x + y; // ; while` / `do {\n\t--x;\n} // meanwhile` | Yes | The `while` that closes the statement is the first one at the statement's own nesting level (paren and brace depth both zero) that follows the end of the body. It is located on a comment/string-masked copy of the line and must be a whole token, so a `while` inside a literal, inside a comment, inside an identifier (`whileCount`), or nested in a braced body or lambda on the same line is never mistaken for it |
| `while` claimed by a nested do-while | `do do { --x; ++x; } while (x > 5); while (x > 0);` | Yes | A nested `do` on the same line claims the next `while` at that nesting level, so the split lands on the outer statement's own terminator rather than the inner one's. The nested `do` is matched as a whole token too, so an identifier that merely contains it (`undo`, `doWork`) never claims a `while` |
| Statement after the closing `while` | `do --x; while (x > 0); while (y > 0) { --y; }` | Yes | The terminator is the first qualifying `while`, not the last, so a sibling `while` loop written after it stays on the re-emitted `while` line instead of being taken for the condition |
| Tier-3 expand | `do x = x + y; while(...)` | Yes | Complex RHS (binary op), chained call, or `new` body moves to its own line |
| Tier-3 assign chained/new RHS | `do x = a.b().c(); while(...)` | Yes | Chained-call or `new`-expression RHS is tier 3 (matches the bare-call / bare-`new` body) |
| Tier-3 with the `while` cuddled onto the body line | `do\n\tx = x + y; while (x < 100);` | Yes | The body is already on its own line, so only the terminator moves: reported as `Do-while while clause must be on its own line.`, the same message the tier-2 shape uses. Covers a binary-operator RHS and a chained-call RHS |
| Tier-3 braced body | `do if (c) { x(); } while (y);` | Yes | A braced statement ends on `}` rather than `;`, so both the body's end and the closing `while` are located from that brace. Covers `if`, `while`, `for`, `switch`, `synchronized`, and try-with-resources bodies, a trailing block comment after the `}`, and the `while` sitting on the next line. A one-line `try`/`catch` or `try`/`finally` takes the identical path (the terminator rule is construct-agnostic) but has no fixture: `RightCurly` is configured `alone` for `LITERAL_CATCH` and `LITERAL_FINALLY`, so a `}` followed by `catch`/`finally` cannot appear in a linted fixture. A try-with-resources has no such continuation and is covered |
| Body shares the `{` line | `do { --x;\n} while (x > 0);` | No | The statement sits on the line the fixer rebuilds, so re-emitting the `do` line without the brace would drop it; reported as `cannot remove braces without losing other content on the brace line` |
| Comment ahead of the own-line `{` | `do\n\t/* note */ {\n\t--x;\n}\nwhile (...)` | No | The `{` is located on a comment/literal-masked copy of the buffer, so a comment ahead of it is found rather than read as the body, but it still occupies the line the fixer rebuilds; reported as `cannot remove braces without losing other content on the brace line` |
| Comment on the `do {` line, the `}` line, or between | `do { // guard` / `} // note` / a comment line before the `while` | Yes | The braces go away but their comments do not: a comment on the `do {` line rides along on the rebuilt `do` line, and one on the `}` line or between it and the `while` is re-emitted ahead of the `while`. Code in those positions has no home and is refused instead |
| Comment on the `do` line plus a second comment on the `{` line or the body | `do // note\n{ // brace note\n\t--x;\n}\nwhile (c);`, `do // note\n{\n\t--x; // pending\n}\nwhile (c);` | No | Only one comment can ride the rebuilt `do` line: a second `//` trailer behind the first would be swallowed by it, and in tier 2 the body joins that same line ahead of its own trailing comment. Reported as `cannot remove braces without losing other content on the brace line` |
| Unterminated block comment or text block on the line it opened | `do /* multi\n\tline */\n\tx = 5;\nwhile (...)`, `do { /* multi\n\tline */ --x;\n} while (...)`, `} /* multi\n\tline */\n\twhile (...)` | No | The literal does not close on that line, so the text below it is literal content rather than code: rebuilding the line would carry the opener away from what it covers, and a brace appended to it would land inside the literal. Applies to the `do` line, the `do {` line, the `}` line, and a non-do-while keyword line; reported as `block comment or text block does not close on the line it opened` |
| Comment ahead of the closing `}` | `do {\n\t--x;\n\t/* note */ } while (x > 0);` | No | The `}` is located on a comment/literal-masked copy of the buffer, so a comment ahead of it still occupies the line the fixer would drop; reported as `cannot remove braces without losing other content on the brace line` |
| Multi-line braced body | `do {\n\t--x;\n\t--y;\n} while(...)` | n/a | Not reported: a body of more than one statement needs its braces, so there is nothing to collapse. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `cannot remove braces from a multi-line do-while body` |
| Another do-while ahead of it on the line | `do do --x; while (x > 5); while (x > 0);` (the inner statement), `do; while (c); do --y; while (y > 0);` | No | The statement is rebuilt from the reported keyword's own indentation, so a do-while written ahead of it on the same line would be dropped. The outer statement is reshaped first, which puts the inner one on a line of its own, and the next pass fixes it; reported as `do-while shares its line with another do-while` |
| Buffer does not parse / no do-while at violation | bare fragment / mid-fix damaged source / stale violation column | No | Both the tier and the terminator's position come from the parse, so neither can be determined when the buffer fails to parse or when it parses but no `do` keyword sits at the reported position. The route refuses immediately rather than re-deriving the terminator from raw text: an indentation-anchored text scan could only pick between refusal strings, never emit a splice. Reported as `cannot tell which do-while form the body needs without a parse` when the buffer did not parse, and `no control-flow body at the reported position; an earlier fix in this pass moved it` when it did |
| Empty braced body | `do {\n} while (c);` | n/a | Not reported: an empty block has no statement to reshape. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `control-flow body is empty` |
| Comment-only braced body | `do {\n\t// note\n} while (c);` | n/a | Not reported: a block holding only comments has no statement in the AST, so there is nothing to collapse. The fixer still refuses one independently, guarding against a stale column or a sibling fixer's rewrite, and reports `do-while body has no statement to reshape` |
| Text block in body | `do s = """..."""; while(...)` | No | Returns a SkipResult; the body's text block spans lines that the reshaped one-line (tier 2) or two-line (tier 3) body cannot carry, so reshaping it would change the block's incidental indentation and therefore its value |
| `while` on a comment/text-block close line | `do\n\tx = 1; /* c\n\t*/ while (...)` | No | SkipResult: "block comment or text block does not close on the line it opened". Every reshape re-emits the terminator's line at the keyword's indent, so a line that begins inside a block comment or text block would carry that literal's content away from its opener |
| Body running onto the terminator's line | `do list\n\t\t.add(1); while (c);` | No | SkipResult: "do-while body runs onto the line its closing while shares". The body opened on the `do` line and continues onto the line the `while` shares, and neither tier form has a second body line to put that text on |
| Body continuing past the `do` line | `do x = x\n\t\t+ 1;\nwhile (c);`, `do x = foo()\n\t\t.bar();\nwhile (c);` | No | SkipResult: "do-while body does not end in a semicolon". Only the text on the `do` line is available to the reshaped body, and it stops mid-expression, so emitting it as the whole body would drop the continuation. The end is tested on a comment/literal-masked copy, so a `;` inside a trailing comment or string does not count as the terminator |
| Comment ahead of the terminator | `do\n\t--x;\n/* note */ while (c);` | Yes | A comment sharing the terminator's line annotates the statement, so it rides on the re-emitted clause instead of being stranded |
| Terminating `while` cuddled onto the body's last line | `do\n\tif (c)\n\t\t--x;\n\telse\n\t\t--z; while (c);\nwhile (d)\n\t--z;` | Yes | The terminator's position comes from the check's AST, so the statement's own `while` is known even when it shares a line with the body. That line splits: the body part stays where it is and the terminator moves down onto the added closing brace. A sibling `while` loop written below at the same indentation is no longer mistaken for the terminator, and neither is a terminator indented differently from its `do` |
